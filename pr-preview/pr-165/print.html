yapi

yapi

yapi is a coding agent for the terminal. Given a task and a working folder, it inspects files, runs commands, edits code and works through multi-step tasks.

yapi is a Rust reimplementation of Pi v1.0.0. It uses Pi’s commands, settings, session files, packages and extension API, so an existing Pi setup works in yapi without changes. It ships as a single native binary and does not require Node.js.

Get started

The Quickstart covers installation, connecting a model and a first task. Pi users can bring their existing setup, as Coming from Pi describes.

  • Use yapi in the terminal to attach files, run commands and direct ongoing work.
  • Choose a model and connect a subscription, API key, cloud provider or local model.
  • Manage sessions to resume work or try another approach without losing history.
  • Configure yapi with settings, project instructions, skills and prompt templates.

Customize yapi

  • Packages bundle extensions, skills, prompt templates and themes, and install from npm, git or a local path.
  • MCP servers connect external tools.
  • Extensions add tools, commands, event handlers and interface components. Pi extensions run unchanged, and native extensions are written in Rust. Choose an extension type compares the two.

Automate yapi

Print, JSON and RPC modes serve scripts, editors and other programs. The formats and protocols are Pi’s, so Pi’s clients work with yapi.

Security

yapi reads files, edits them and runs commands with the user’s permissions, and it does not ask before each tool call. Extensions run in a WebAssembly sandbox with memory and compute limits. Read Security model and sandboxing before using yapi with untrusted repositories, packages or unattended automation.

Project status

Differences from Pi lists every known difference, including Pi features not yet ported. The Roadmap lists planned work, and Performance compares startup time, memory and install size with Pi. Report problems in the issue tracker.

Quickstart

yapi runs in your terminal and works with the files on your machine. It needs a model, through a subscription, an API key or a local server.

1. Install yapi

On Linux or macOS, run the install script:

curl -fsSL https://raw.githubusercontent.com/SkymanOne/yapi/main/install.sh | sh

It installs yapi in ~/.local/bin. Install yapi covers the other methods. Check the installation:

yapi --version

2. Start yapi

Start yapi in the folder it should work in:

cd ~/code/my-project
yapi

yapi uses the working folder to find files, project instructions and configuration, and to group saved sessions.

3. Choose a model

Run /login, choose a provider and follow the prompts to sign in with a subscription or save an API key. Run /model to choose another model.

yapi also reads API keys from the environment, such as ANTHROPIC_API_KEY. Choose a model lists every provider.

4. Give yapi a task

Type a task and press Enter. yapi shows each file it reads, each command it runs and each edit it makes. It does not ask before each tool call.

Explain how requests flow through src/server.rs
Find why `cargo test` fails and fix it
@Cargo.toml Which dependencies are outdated?
!git status

@path attaches a file. !command runs a shell command and sends its output to the model, and !!command runs it without sending the output. Press Escape to stop the agent and Ctrl+C twice to quit.

Review the changes when yapi finishes. Keep important work under version control, and use a container for untrusted or unattended work. See Security model and sandboxing.

Continue later

yapi saves sessions automatically. To resume the most recent session in a folder, run:

yapi -c

Use /resume to choose another session. See Manage sessions.

Install yapi

yapi is one executable. Releases include builds for Linux and macOS on x86_64 and arm64, and other platforms can build it from source. Linux and macOS are fully supported. Windows support is best effort.

Install script

curl -fsSL https://raw.githubusercontent.com/SkymanOne/yapi/main/install.sh | sh

The script downloads the latest release for your system, verifies its SHA-256 checksum and installs it as ~/.local/bin/yapi. It also installs the documentation for the model.

OptionVariableEffect
--version <tag>YAPI_VERSIONInstall that release, such as v0.1.0
--to <dir>YAPI_INSTALL_DIRInstall into <dir>
--no-docsYAPI_NO_DOCS=1Skip the documentation for the model

Pass options after sh -s --:

curl -fsSL https://raw.githubusercontent.com/SkymanOne/yapi/main/install.sh | sh -s -- --version v0.1.0 --to /usr/local/bin

cargo-binstall

cargo-binstall installs the same release binary into ~/.cargo/bin:

cargo binstall --git https://github.com/SkymanOne/yapi yapi

Keep --git, because the yapi crate on crates.io is an unrelated project. cargo-binstall installs the release that the manifest on main names. If it reports that the release does not exist, use the install script.

Release archives

Each release has a yapi-<target>.tar.gz archive per platform, with a .sha256 checksum. The archive holds yapi and its license files.

TargetSystems
x86_64-unknown-linux-gnuLinux on x86_64 with glibc 2.35 or newer, such as Ubuntu 22.04, Debian 12 and Fedora 36
aarch64-unknown-linux-gnuLinux on arm64 with glibc 2.35 or newer
x86_64-apple-darwinmacOS on Intel
aarch64-apple-darwinmacOS on Apple silicon

Download an archive, verify it and unpack yapi into a directory on PATH:

curl -fsSLO https://github.com/SkymanOne/yapi/releases/latest/download/yapi-x86_64-unknown-linux-gnu.tar.gz
curl -fsSLO https://github.com/SkymanOne/yapi/releases/latest/download/yapi-x86_64-unknown-linux-gnu.tar.gz.sha256
sha256sum -c yapi-x86_64-unknown-linux-gnu.tar.gz.sha256
tar xzf yapi-x86_64-unknown-linux-gnu.tar.gz -C ~/.local/bin yapi

On macOS, verify with shasum -a 256 -c. For a specific release, replace latest/download with download/<tag>. Systems with an older glibc, or with musl such as Alpine, need to build from source. If macOS refuses to open a binary downloaded in a browser, see Troubleshooting.

Build from source

yapi builds with Rust 1.99 or newer. Install Rust with rustup, then run:

cargo install --locked --git https://github.com/SkymanOne/yapi --tag v0.1.0 yapi

Cargo installs yapi in ~/.cargo/bin. Leave out --tag to build the latest commit on main. To build from a clone, run cargo install --locked --path crates/yapi in it. If Cargo reports that rustc is too old, run rustup update.

Check the installation

yapi --version

Documentation for the model

yapi reads its own documentation to answer questions about its features. The documentation holds these pages and Pi’s docs and examples, which describe the extension API. Each release publishes it as yapi-docs.tar.gz, which goes to ~/.yapi/agent/docs, or docs in YAPI_CODING_AGENT_DIR when that is set.

The install script installs the documentation with the binary. With any other method, yapi downloads it in the background on first start. Either way, the archive is verified against its checksum and replaces the previous copy. YAPI_NO_DOCS=1, --offline and PI_OFFLINE=1 turn the download off. Until a copy for its own version is in place, yapi points the model to the online documentation. Pi’s pages use Pi’s names, such as ~/.pi/agent, and Coming from Pi lists yapi’s.

To install it by hand, such as on a machine that runs offline:

mkdir -p ~/.yapi/agent/docs && curl -fsSL https://github.com/SkymanOne/yapi/releases/latest/download/yapi-docs.tar.gz | tar xzf - -C ~/.yapi/agent/docs

For an older yapi, replace latest/download with download/v<version>, where <version> is what yapi --version prints. yapi replaces these files on upgrade, so keep your own notes elsewhere.

Upgrade

yapi does not update itself. yapi update prints how to upgrade, yapi update --extensions updates packages and yapi update --models updates model catalogs. Upgrade yapi the same way you installed it:

Installed withUpgrade
Install scriptRun the script again.
cargo-binstallRun the same cargo binstall command again.
Release archiveUnpack the new archive over the old binary.
CargoRun cargo install again with the new release’s tag.

Settings, credentials, sessions and packages are kept.

In the terminal, yapi checks at startup for a newer release and for package updates, and shows a notice when it finds one. PI_SKIP_VERSION_CHECK=1 turns off the release check. --offline and PI_OFFLINE=1 turn off both.

YAPI_RELEASES_URL points the install script, the release check and the documentation download at another releases page, such as a mirror. It defaults to https://github.com/SkymanOne/yapi/releases.

Uninstall

  • Install script or release archive: delete ~/.local/bin/yapi, or the file in the directory you chose.
  • cargo-binstall or Cargo: run cargo uninstall yapi.

To remove settings, credentials, sessions, packages and caches as well, delete ~/.yapi, or YAPI_CODING_AGENT_DIR when set, and each project’s .yapi folder.

Coming from Pi

yapi reads Pi’s formats but keeps its own folders, so the two never write the same files. To copy an existing Pi setup, run:

yapi import pi

The command copies Pi’s agent folder, ~/.pi/agent or PI_CODING_AGENT_DIR, into yapi’s: settings, credentials, models, key bindings, MCP servers and their sign-ins, trust decisions, the global AGENTS.md or CLAUDE.md, SYSTEM.md and APPEND_SYSTEM.md, sessions, prompt templates, skills, themes, extensions and packages. It also copies the current project’s .pi folder into .yapi.

Files yapi already has are kept, except a settings.json that holds only the version yapi recorded on first start. Pi’s lastChangelogVersion is left out, because it holds Pi’s version.

After the import, yapi and Pi work side by side, and each opens the other’s session files.

Display modes

yapi draws in fullscreen mode by default. Regular mode keeps the transcript in the terminal’s scrollback instead. Switch with /settings or --tui-mode regular.

In fullscreen mode, yapi handles the mouse:

  • The wheel scrolls the transcript. Hold Alt to scroll five times as far. “Fullscreen wheel scrolling” in /settings sets a fixed number of lines per step.
  • Drag to select text. A double click selects a word or path, and a triple click selects a line. Releasing the button copies the selection. With “Fullscreen copy on select” off, press Ctrl+X to copy it.
  • A click on a tool call, thinking, a skill or a summary expands or collapses it. Ctrl+O and Ctrl+T still set every item at once.
  • A click on a web or mail link opens it, and a click on a file link shows the file in its folder. Other links do not open, so a click never starts a program. See Links.
  • A click in the editor, a list or a dialog moves the cursor or chooses the item.
  • Drag the scrollbar’s thumb, or click its track to jump. With “Fullscreen scrollbar” set to auto, pointing at the scrollbar shows it, except inside tmux, Zellij and GNU Screen.

Pi publishes catalog updates between releases. yapi fetches them for the providers you have configured: at startup, when the model selector opens, after /login and with yapi update --models. Manage sessions

yapi saves every conversation as a JSONL file under ~/.yapi/agent/sessions/, grouped by project. The format is Pi’s, so Pi and yapi open each other’s sessions.

Continue work

yapi -c                      # continue the last session in this folder
yapi -r                      # pick a session to resume
yapi --session 3f2a          # open a session by file or id prefix
yapi --fork 3f2a             # copy a session into a new one
yapi --no-session            # do not save this run

Inside yapi, /resume opens the session picker, /new starts a fresh session and /name names the current one.

Branch a session

A session is a tree. When you go back to an earlier message, the abandoned branch is kept, so no work is lost.

  • /tree shows every branch and jumps to any earlier point. By default, pressing Escape twice on an empty editor opens it too. The doubleEscapeAction setting changes this to fork or none.
  • /fork starts a new session from an earlier message.
  • /clone duplicates the current session.

Compact context

Long sessions fill the model’s context window. yapi summarizes older messages automatically before that happens. /compact runs it on demand, and /settings turns automatic compaction off.

Export and import

/export writes the session to a standalone HTML file. yapi --export <file>.jsonl [output.html] does the same for a session file from the command line. /export <path>.jsonl writes the current branch as a new session file, without the other branches.

/import <path>.jsonl copies a session file into the project’s session folder and resumes it.

Security model and sandboxing

yapi reads files, edits them and runs commands on your machine. This page describes what yapi protects, what it leaves to the operating system, and how extensions are isolated.

Security model

yapi runs with the permissions of the user who starts it. The built-in tools read, bash, edit and write are not sandboxed, and yapi does not ask for approval before each tool call. A command the model runs can read or change any file, and reach any service, that the user can.

Treat the commands and code the model generates as untrusted. Files, comments and command output that the model reads can steer it through prompt injection. Reviewing the transcript and granting project trust do not create a security boundary.

ComponentRuns asAccess
Built-in tools and ! commandsyapi’s process and its child processesEverything the user can access
ExtensionsWebAssembly instancesWhat their grants allow. In v0.1, Pi’s defaults: files, processes, network and environment.
Processes that extensions start, including subagentsChild processes, outside the sandboxEverything the user can access
MCP servers over stdioChild processesEverything the user can access
MCP servers over HTTPRemote servicesWhat the server allows
Codemode scriptsFresh WebAssembly instances with no grantsOnly the tools they call, and the clock and time zone as in Pi

For untrusted repositories, unfamiliar packages or unattended runs, isolate yapi at the operating-system level:

  • Run yapi in a container or virtual machine that holds only the files the task needs.
  • Provide only the credentials the task needs, preferably short-lived and narrowly scoped.
  • Restrict network access when the task does not need it.
  • Keep important work under version control.

Sandboxing

Every extension runs in a WebAssembly instance hosted by Wasmtime, separate from yapi’s own memory. The sandbox limits what extension code can do directly. It does not restrict the built-in tools, child processes or MCP servers.

Instances and limits

An instance is a trust domain. All Pi extensions share one QuickJS-NG instance, because grants cannot be enforced between packages that share a JavaScript realm. Each native extension gets an instance of its own, and codemode gets a fresh instance with no grants for every script.

Each call into an instance may compute for 60 seconds, not counting time spent waiting on yapi. Each extension instance may use 1 GiB of memory, and each codemode instance 384 MiB. An instance runs one call at a time, so a long computation in one Pi extension delays the other Pi extensions. An instance that traps, for example by exceeding a limit, is restarted and its extensions are reloaded.

Grants

The host checks every file, process, network and environment access against the extension’s grants. In v0.1, every package receives Pi’s default grants, which allow all four, so an extension can do what it could do in Pi. Per-package grants that you approve are planned, as the Roadmap describes.

A process grant amounts to all four in practice. The host checks each grant separately, but a process an extension starts runs as the user, outside the sandbox, and inherits yapi’s environment, including API keys. A subagent is such a process: a full yapi with the user’s installed packages.

An extension can register a stdio MCP server only with the process grant, and an HTTP server only with the network grant.

Agent sessions and events

yapi never runs an agent session inside an extension’s instance, because that session would run tools and use credentials outside the extension’s grants. Subagents run as separate yapi processes instead.

Extensions share Pi’s pi.events bus, so every extension receives the events of every other extension.

Project trust

Files in a project’s .yapi folder can change how yapi behaves and can run code: settings.json, mcp.json, extensions, skills, prompts, themes, SYSTEM.md and APPEND_SYSTEM.md, as well as an .agents/skills folder in the project or a parent folder. Until the project is trusted, yapi loads none of them, and no project extension runs.

The first time interactive mode starts in a project that has them, yapi asks whether to trust it. Print, JSON and RPC modes never ask, and treat the project as untrusted unless a decision applies.

  • yapi saves the decision in ~/.yapi/agent/trust.json. /trust changes it later.
  • --approve and --no-approve decide for one run.
  • "defaultProjectTrust" in global settings set to "always" or "never" decides without asking.

AGENTS.md and CLAUDE.md load whether or not the project is trusted. Treat their contents as untrusted input as well.

Use the project of another folder

--project-dir <dir> takes the project from another folder, as if yapi had started there. yapi loads that folder’s .yapi files and the AGENTS.md or CLAUDE.md of that folder and its parents, and applies trust to that folder, including --approve and --no-approve. The working folder’s own .yapi folder does not load. A relative path is resolved against the working folder.

Tools, the session and extensions’ ctx.cwd stay in the working folder. A native extension finds the project folder with project_dir(). Subagents use the flag to work in one folder with their parent’s project.

Automate yapi

yapi runs without its interface for scripts, editors and other programs. The output formats and protocols are Pi’s, so Pi’s clients work with yapi.

Print mode

-p sends one message, prints the answer and exits:

yapi -p "Summarize the open TODOs in src/"
git diff | yapi -p "Write a commit message for this diff"
yapi -p @report.md @chart.png "What does the chart show?"

Piped input becomes part of the first message, and @path attaches files and images.

JSON mode

--mode json prints one JSON event per line for the whole run: message updates, tool calls, tool results and the final state. Pi’s JSON documentation describes the events.

yapi --mode json -p "List the crates in this workspace"

RPC mode

--mode rpc keeps yapi running and reads commands from stdin, one JSON object per line. Responses and events go to stdout. Clients can prompt, steer, abort, switch models and sessions, and answer extension dialogs. Pi’s RPC documentation lists the commands, and Pi’s RpcClient works with yapi.

yapi --mode rpc --no-session

Project instructions

yapi reads one instruction file from the working folder and from each parent folder, and adds them to the system prompt. In each folder it takes the first of AGENTS.override.md, AGENTS.md and CLAUDE.md that exists. Use them for build commands, conventions and anything else the agent should know about the project.

Skills and prompt templates

Skills follow the Agent Skills specification. Each skill is a folder with a SKILL.md file. yapi lists every skill’s name and description in the system prompt, and the model reads the full instructions when a task calls for them. /skill:name loads one directly.

Prompt templates are Markdown files that become slash commands. Save this as ~/.yapi/agent/prompts/review.md:

---
description: Review staged git changes
argument-hint: "[focus]"
---
Review the staged changes. Focus on ${1:-correctness and error handling}.

/review then sends the prompt, and /review concurrency fills in the focus. Pi’s prompt template documentation lists every argument form.

Themes

Choose a theme in /settings or with "theme" in settings. --use-theme <name> applies one for a single run. Theme files use Pi’s JSON format, described in Pi’s theme documentation.

Key bindings

~/.yapi/agent/keybindings.json changes the keys. Pi’s key binding documentation lists the format and every action. /hotkeys shows the bindings in effect.

Images

yapi prepares images in prompts, @path arguments and tool results before they reach the model:

  • Images that are not PNG, JPEG, GIF or WebP are converted to PNG when they are BMP, TIFF, ICO, PNM, HDR, DDS or farbfeld. This applies to images that arrive with a MIME type: RPC and SDK prompts, tool results and the clipboard. @path arguments and the read tool only recognize PNG, JPEG, GIF, WebP and BMP files, so other formats are read as text.
  • With "images": {"autoResize": true}, the default, larger images are scaled down to fit 2000×2000 pixels and 4.5 MiB as base64, or the model’s own limits. A scaled image may be sent as JPEG, with a note that gives the model its original size.
  • A prompt or read image that cannot be converted or made to fit is left out, with a note that says so. A tool result keeps its original image unchanged.
  • A pasted clipboard image that is not PNG, JPEG, WebP or GIF is converted to PNG when pasted, ignoring its EXIF orientation.
  • "images": {"blockImages": true} keeps all images from the model.

Both settings are also in /settings.

Links

In a terminal that supports hyperlinks, Markdown links show only their text, and the paths in read, write, edit and ls calls link to their files. In other terminals, a Markdown link shows its URL after its text.

yapi detects hyperlink support in common terminals, such as iTerm2, Ghostty, kitty, WezTerm and VS Code, and asks tmux whether it passes hyperlinks on. Set "terminal": {"hyperlinks": true} or false to override the detection. The PI_HYPERLINKS environment variable, 1 or 0, does the same, and the setting takes precedence.

Use packages

A package bundles extensions, skills, prompt templates and themes. yapi installs Pi packages from npm, git or a local folder, with no Node.js required.

Install and manage packages

Package manifests

yapi reads the pi key of package.json to find a package’s resources. An optional yapi key with the same shape takes precedence, so one package can ship a native build for yapi and JavaScript for Pi. Packages without a manifest use the conventional folders: extensions, skills, prompts and themes. yapi loads .wasm files from extensions as native extensions.

npm client

yapi has a built-in npm client. It resolves versions with npm’s range syntax, verifies integrity hashes and lays out node_modules as npm does. It does not run lifecycle scripts, which mostly build native addons that the WebAssembly runtime cannot load. Such addons are installed unbuilt and fail only if an extension loads one.

The client reads registries and credentials from npm_config_* environment variables and from ~/.npmrc, or the file npm_config_userconfig names. //npm.acme.dev/:_authToken=${ACME_NPM_TOKEN}

Pi’s npmCommand setting replaces the built-in client for installing and updating npm sources. Removals and the dependencies of git packages always use the built-in client.

Connect MCP servers

yapi connects to Model Context Protocol servers over stdio and streamable HTTP. Describe them in ~/.yapi/agent/mcp.json, or in .yapi/mcp.json for one project:

{
  "mcpServers": {
    "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "."] },
    "docs": { "url": "https://example.com/mcp", "headers": { "Authorization": "Bearer ${DOCS_TOKEN}" } }
  }
}

Pi’s MCP documentation describes every option.

Manage servers

yapi mcp edits the file and checks servers without starting a session:

yapi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
yapi mcp add docs --url https://example.com/mcp --bearer-token-env-var DOCS_TOKEN
yapi mcp list                 # state, tools and errors, exits 1 if a server fails
yapi mcp remove docs

Inside yapi, /mcp opens a manager that lists each server with its state, tool count, exposure and configuration file. Select a server to see its tools, reconnect, sign in or out, change its exposure, or enable or disable it. Exposure and enabled changes are saved to the mcp.json that defines the server. Outside interactive mode, /mcp prints the status, and /mcp login, /mcp logout and /mcp reconnect act on a server directly.

Sign in

HTTP servers without an Authorization header sign in with OAuth. A server that needs a sign-in shows it in /mcp and yapi mcp list. Select it in /mcp, or run /mcp login <server> inside yapi or yapi mcp login <server> in a terminal. logout deletes the stored credentials.

yapi opens the authorization page in your browser and waits for the redirect. If the browser runs on another machine, paste the URL it was redirected to. yapi registers itself with servers that allow it. For other servers, set a pre-registered client in the server’s oauth object (clientId, clientSecret, callbackPort or callbackUrl, scope, clientName, authServerMetadataUrl), or pass --oauth-client-id and the related options to yapi mcp add.

yapi stores credentials in ~/.yapi/agent/mcp-auth.json, in Pi’s format, and refreshes access tokens before they expire. A running session picks up a sign-in made with yapi mcp login on its next turn.

To send the token of a provider you signed in to with /login instead, add "auth": { "provider": "<provider>" } to a server in the global mcp.json.

Servers from extensions

An extension adds a server for the session with pi.registerMcpServer(name, config), where config takes the same fields as an mcp.json entry, and removes it with pi.unregisterMcpServer(name). A server of the same name in mcp.json takes precedence. Changes to a registered server in /mcp last for the session only.

A stdio server needs the extension’s process grant, and an HTTP server its network grant. Every package has both by default. As in Pi, registerMcpServer throws for a name that another extension registered, or one whose tool prefix would clash with it, such as my_docs after my-docs. During loading, the error fails the extension’s load, and the extension that loaded first keeps the name.

Codemode

By default, yapi offers MCP tools through codemode. Instead of one tool call per step, the model writes a short JavaScript program that calls several tools and combines their results. Programs run in a fresh WebAssembly sandbox with no file, process or network access of their own.

  • "exposure": "direct" on a server offers its tools to the model directly.
  • --tools read,bash,edit,write,codemode routes the built-in tools through codemode as well.
  • "codemode": { "mode": "only" } in settings.json offers the tools that scripts can call only through codemode.

The first prompt does not wait for servers whose tools only codemode reaches. A script that names a server’s tools, such as tools.mcp__docs__search, waits until that server has connected or failed to connect. A script that searches, lists or describes tools waits for every server that is still connecting. Aborting the turn ends the wait.

A package that registers its own codemode tool replaces the built-in one, and yapi warns about it at startup.

Scripts can also use the models global to list the catalog and run classifier and image models with the session’s credentials. Pi’s codemode documentation describes the scripting API.

Extensions

Extensions add tools, commands, flags, event handlers and interface components. yapi runs two types on one WebAssembly host:

  • Pi extensions, written in TypeScript or JavaScript and usually distributed through npm, run unchanged.
  • Native extensions are written in Rust and compiled to WebAssembly components.

Both types load from the same places, ship in the same packages and use the same events and interface model.

Pi extensions are the better choice when:

  • the extension should also run in Pi, or already exists as a Pi package
  • it needs parts of Pi’s API that the native SDK does not cover yet: providers, MCP servers, model classification and image generation, and session actions such as ctx.newSession and ctx.fork
  • it builds on npm libraries, or benefits from editing without a build step

Native extensions are the better choice when:

  • the extension does heavy computation, which compiled code runs much faster than an interpreter
  • it should be isolated from other extensions. A native extension’s crash does not reload the others, and its instance is the unit that per-package grants will apply to.
  • memory matters. Native extensions do not load the JavaScript runtime. In the benchmark, ten small Pi extensions raise idle memory on Linux from 18.8 MB to 40.0 MB.
  • the code base is in Rust, or should use Rust crates

Weigh these limits as well:

  • A Pi extension that needs Node features the runtime lacks, such as native addons, net and tls servers or worker_threads, cannot run in yapi. Differences from Pi lists them.
  • A native extension needs the Rust toolchain to build, and may need to be rebuilt for a new yapi release until 1.0.
  • One package can ship both types. A yapi key in package.json names the native build for yapi, and the pi key names the JavaScript build for Pi. See Package manifests.

Load extensions

yapi loads extensions from:

  • ~/.yapi/agent/extensions, and .yapi/extensions in a trusted project
  • packages and files added with yapi install, which accepts npm and git sources, local folders and single .ts, .js or .wasm files
  • -e <source> for one run, which accepts a file, a package folder, or an npm or git source

yapi -ne starts without extensions, and yapi config turns single extensions off.

/reload loads every extension again from disk, so edits and rebuilt native extensions take effect. A new, resumed, forked or cloned session picks up added and removed extension files and installs packages added to settings, but keeps the extensions it already loaded until /reload. A session in another working folder loads every extension again.

Write a Pi extension

Extensions use Pi’s API. Save this as ~/.yapi/agent/extensions/hello.ts:

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerCommand("hello", {
    description: "Show a greeting",
    handler: async (name, ctx) => {
      ctx.ui.notify(`Hello, ${name || "world"}!`, "info");
    },
  });
}

Start yapi and run /hello Ada. Pi’s extension documentation covers tools, events, UI components and the rest of the API.

How Pi extensions run

Pi extensions run in yapi-js, a QuickJS-NG runtime compiled to WebAssembly, so yapi needs no Node.js.

  • @earendil-works/pi-coding-agent, pi-ai, pi-agent-core, pi-tui and typebox resolve to copies bundled with yapi.
  • yapi resolves modules as Node does and strips TypeScript types, with a cache keyed by file content.
  • Shims provide Node’s fs, path, os, child_process, events, stream, util, crypto hashes, buffer, timers, fetch, dns.lookup and Intl. Native addons, net and tls servers and worker_threads fail when used, and the rest of the extension keeps working.
  • Dates use the local time zone, from TZ or the system, as in Node.
  • Interface components render inside the runtime. yapi paints their last frame, so a slow extension never blocks the interface.

Differences from Pi lists where the behavior differs.

Crashes

Security model and sandboxing describes the limits of each instance and what extensions may access. A crashed instance restarts and its extensions reload. yapi reports the crash as an extension error, closes the instance’s dialogs and widgets, and restores the built-in editor, footer and header. Tool calls and messages it drew stay in the transcript and are drawn again by the restarted instance.

Providers from extensions

pi.registerProvider() adds a provider and its models. They appear in /model and work with --model and RPC’s set_model.

  • A provider configured like a models.json entry streams through yapi’s implementation of its api.
  • A provider with its own streamSimple can implement an API yapi does not have, or hand requests to pi-ai’s built-in APIs, such as anthropicMessagesApi(). A stream registered with pi-ai’s registerApiProvider serves every model of its API, including ones from models.json. Provider hooks such as before_provider_request run either way.
  • A provider with oauth adds its sign-in to /login. yapi stores its credentials in auth.json and refreshes them before they expire.
  • A provider with refreshModels updates its model list whenever yapi refreshes model catalogs.

Pi’s custom provider documentation describes the configuration.

Native extensions in Rust

Native extensions are WebAssembly components written in Rust with the yapi-extension-api crate. Like Pi extensions, they register tools, commands, flags, event handlers and interface components, and they use Pi’s JSON shapes for events and results. Each one runs in a WebAssembly instance of its own, with no JavaScript runtime, and builds to one .wasm file of a few hundred kilobytes.

The native extension API is unstable until yapi 1.0. The WIT world, the Rust SDK and the host requests may change in any release before then, and extensions may need to be rebuilt. Pi extensions are not affected.

Create an extension

The SDK needs Rust 1.88 or newer, or 1.91 with the widgets feature. Add the wasm32-wasip2 target to your Rust toolchain:

rustup target add wasm32-wasip2

Create a project:

yapi new shout

yapi new writes a Cargo project that is also a yapi package:

shout/
├── .cargo/config.toml   makes wasm32-wasip2 the default target
├── .gitignore
├── Cargo.toml           a cdylib crate that depends on yapi-extension-api 0.1.0
├── README.md
├── extensions/          where the built extension goes
├── package.json         names extensions/shout.wasm for yapi
└── src/lib.rs           the hello example, to replace with your own

The package takes the directory’s name, or the one --name gives. Names use lowercase ASCII letters, digits, - and _, and start with a letter. The same template works with cargo-generate:

cargo generate --git https://github.com/SkymanOne/yapi --tag v0.1.0 crates/yapi/templates/extension

To start without the template, create a library crate with crate-type = ["cdylib"] and depend on the SDK version of the yapi release you target:

[dependencies]
yapi-extension-api = "0.1.0"

An extension registers its features in an init function and exports it with extension!. Tools, commands and event handlers are async closures:

#![allow(unused)]
fn main() {
// src/lib.rs
use yapi_extension_api::{Api, Tool, ToolResult, json, notify};

fn init(api: &mut Api) {
    api.register_tool(Tool::new(
        "shout",
        "Repeats the text in capitals",
        json!({
            "type": "object",
            "properties": {"text": {"type": "string"}},
            "required": ["text"]
        }),
        |params, _ctx| async move {
            let text = params["text"].as_str().unwrap_or_default();
            Ok(ToolResult::text(text.to_uppercase()))
        },
    ));
    api.register_command("hello", "Says hello", |args, _ctx| async move {
        let name = if args.is_empty() { "world" } else { &args };
        notify(&format!("Hello, {name}!"), "info");
        Ok(())
    });
}

yapi_extension_api::extension!(init);
}

Build it and copy the result into the package:

cargo build --release
cp target/wasm32-wasip2/release/shout.wasm extensions/

A crate without the template’s .cargo/config.toml builds with cargo build --release --target wasm32-wasip2.

Try it

Load the package for one run without installing it:

yapi -e .

-e also takes the .wasm file itself.

To check that the package loads without a model or network access, run check-extension.py from the agent skills. It prints the registered commands and any load errors, and exits with status 1 on an error:

python3 check-extension.py .

Install it

yapi install takes the package folder or the .wasm file:

yapi install .       # for every project
yapi install . -l    # for this project only

yapi records the path in settings.json and loads the file in place, so a rebuild takes effect after /reload or a restart. yapi list shows the extension, yapi remove <path> uninstalls it and yapi config turns it off.

Share it

Share a native extension as a package that contains the built .wasm file. A project from yapi new is already one. Commit extensions/shout.wasm with the sources and push the repository, and others can install it by URL:

yapi install git:github.com/you/shout

To publish on npm, run npm publish. Others then install it with yapi install npm:shout. The template’s package.json publishes only the extensions folder.

A package needs no manifest, because yapi loads every .wasm file in its extensions folder. A manifest can name the files instead. yapi reads its yapi key before the pi key, so one package can ship a native build for yapi and a JavaScript build for Pi:

{
  "name": "shout",
  "version": "0.1.0",
  "pi": { "extensions": ["./dist/shout.js"] },
  "yapi": { "extensions": ["./dist/shout.wasm"] }
}

Commit or publish the built .wasm file, not only the Rust sources. yapi never compiles code during installation, because a build runs build.rs scripts and procedural macros outside the sandbox.

Processes

Process::spawn starts a process that runs while the extension does other work. It takes {"command", "args", "cwd", "env", "envAdd", "stdin"}, all optional except command. Without cwd the process starts in yapi’s working folder, env replaces the whole environment, envAdd adds variables to the inherited environment or to env, and "stdin": "ignore" gives it empty standard input instead of a pipe. Process::next waits for the next ProcessEvent: output on standard output or standard error, then the exit. A next future dropped before it finishes loses no output. write waits while the process has not taken the previous write, and close_stdin and kill act at once.

Dropping a Process kills it, and so does stopping the extension. Starting one needs the process grant, which every extension has by default.

A process inherits yapi’s environment, so envAdd is how an extension gives it a variable without the environment grant. yapi adds the variables itself, and the extension never sees the values the process inherits:

#![allow(unused)]
fn main() {
let output = request("exec.sync", &json!({
    "command": "sh",
    "args": ["scripts/build.sh"],
    "envAdd": {"BUILD_MODE": "release"},
}))?;
}

Where the extension is

extension_path() returns the extension’s .wasm file as file, and the root of the package it was installed from as package_root. package_root is None for a file given with -e or found in an extensions folder. An extension that starts another yapi with itself loaded passes file to -e, and one that ships scripts or data finds them next to file or under package_root.

Where the project is

project_dir() returns the folder the session’s project files come from, the same folder as projectDir in Context::data. It is the working folder unless yapi runs with --project-dir. The init function can call it before any Context exists, such as to list project files in a tool’s description. yapi runs the init function again for every new, resumed, forked or reloaded session, and each run sees the project of the session it loads for. Older versions of yapi answer None, and an extension then falls back to the working folder from the cwd request.

Events between extensions

events::emit(channel, &data) and events::on(channel, handler) are Pi’s pi.events, a bus that every extension shares, native or Pi, whichever runtime it runs in:

#![allow(unused)]
fn main() {
use yapi_extension_api::events;

fn init(api: &mut Api) {
    events::on("deploy:done", |data| {
        let version = data["version"].as_str().unwrap_or_default();
        notify(&format!("Deployed {version}"), "info");
    });
    api.register_command("deploy", "Deploys", |_args, _ctx| async move {
        events::emit("deploy:done", &json!({"version": "1.2.0"}));
        Ok(())
    });
}
}

emit runs the extension’s own handlers for the channel before it returns, in the order they subscribed, as Pi does. Other extensions receive a JSON copy of the data after emit returns, in the order the extension emitted it.

on returns a Subscription, and Subscription::unsubscribe stops the handler. Dropping the Subscription keeps the handler. A handler runs to completion before the next one starts, so a handler that waits for host work starts it with spawn. When the extension loads again for another session, yapi drops every handler and the init function subscribes again.

A busy runtime holds at most 64 events from other runtimes. yapi drops later ones until it catches up and logs a warning, so a stuck extension never holds up the others or the interface.

Interface components

A component implements the Component trait. render returns the lines to show at a width, as text with ANSI escape sequences. The optional handle_input receives raw terminal input while the component has focus, and handle_mouse receives mouse events in fullscreen mode and returns whether it took them.

#![allow(unused)]
fn main() {
use yapi_extension_api::{Component, CustomOptions, Done, parse_key, theme};

struct Confirm {
    done: Done<bool>,
}

impl Component for Confirm {
    fn render(&mut self, _width: usize) -> Vec<String> {
        vec![theme().fg("accent", "Deploy now? (y/n)")]
    }

    fn handle_input(&mut self, data: &str) {
        if data == "y" || data == "n" {
            self.done.finish(data == "y");
        } else if parse_key(data).as_deref() == Some("escape") {
            self.done.finish(false);
        }
    }
}

api.register_command("deploy", "Deploys after asking", |_args, ctx| async move {
    let confirmed = ctx.custom(|done| Confirm { done }, CustomOptions::default()).await;
    if confirmed == Some(true) {
        // ...
    }
    Ok(())
});
}

Replacing the editor

Context::set_editor_component puts an EditorComponent in place of the built-in editor, as Pi’s setEditorComponent does, or restores the built-in one with None. The editor starts with the built-in editor’s text. yapi calls its set_text, add_to_history, insert_text_at_cursor and configure methods, and the editor reports back with editor_changed when its text changes, editor_submit when the user submits, editor_action for app keys such as app.interrupt, and editor_shortcut for extension shortcuts.

widgets::CustomEditor is Pi’s CustomEditor: the built-in editor’s keys, history, completions and app keys. Wrap it to change how it handles keys or renders, as Pi’s examples extend it. The modal-editor example adds vim-like modes this way.

Tool and message renderers

Tool::render_call and Tool::render_result draw a tool’s call and result in the transcript, as Pi’s renderCall and renderResult do, and Tool::render_shell("self") says they draw the tool’s whole box. Api::register_message_renderer draws custom messages of one type, as Pi’s registerMessageRenderer does. A renderer returns a component, or None to keep yapi’s own rendering.

A tool renderer gets a RenderContext, with Pi’s context fields such as toolCallId, expanded and isPartial in data, and a state value that the call’s and the result’s renderers share for one tool call. Pi’s lastComponent has no counterpart, so a renderer builds a new component each time yapi asks. The new component takes the old one’s place, and yapi shows the old one’s lines until the new one has rendered.

Terminal input and completion

Context::on_terminal_input adds a listener for raw terminal input, as Pi’s ctx.ui.onTerminalInput does. It sees each key before the editor and everything else, in the order listeners were added, and returns TerminalInput::Pass to let the key through, Consume to stop it, or Replace(data) to hand on data in its place, as Pi’s undefined, {consume: true} and {data}. The listener stops when the returned Subscription is dropped or unsubscribe is called, so keep it for as long as the listener should run. editor_text() returns the editor’s text, as Pi’s ctx.ui.getEditorText does, so a listener can take keys only while the editor is empty:

#![allow(unused)]
fn main() {
use std::cell::RefCell;
use yapi_extension_api::{Subscription, TerminalInput, editor_text, parse_key};

thread_local! {
    static LISTENER: RefCell<Option<Subscription>> = const { RefCell::new(None) };
}

api.on("session_start", |_event, ctx| async move {
    let listener = ctx.on_terminal_input(|data| {
        if parse_key(data).as_deref() == Some("down") && editor_text().is_empty() {
            // ...
            return TerminalInput::Consume;
        }
        TerminalInput::Pass
    });
    LISTENER.set(Some(listener));
    Ok(None)
});
}

Context::add_autocomplete_provider adds an AutocompleteProvider over the editor’s completion, as Pi’s ctx.ui.addAutocompleteProvider does. suggestions answers the Suggestions for an EditorState, with Pi’s AutocompleteItem shapes as items, and apply answers the editor after an item is chosen. Each gets a Current, Pi’s current, which answers for the providers added before, over the built-in completion of commands and paths. apply defaults to Current::apply, and trigger_characters names characters that open completion as @ does. The cursor’s column in EditorState counts bytes, so it slices the line directly.

#![allow(unused)]
fn main() {
use yapi_extension_api::{AutocompleteProvider, Current, EditorState, Suggestions, json};

struct Tickets;

impl AutocompleteProvider for Tickets {
    async fn suggestions(&self, state: &EditorState, force: bool, current: &Current) -> Option<Suggestions> {
        let line = &state.lines[state.cursor_line];
        if !line[..state.cursor_col].ends_with('#') {
            return current.suggestions(state, force).await;
        }
        let item = json!({"value": "#42", "label": "#42", "description": "Fix the build"});
        Some(Suggestions { items: vec![item], prefix: "#".into() })
    }
}

ctx.add_autocomplete_provider(Tickets);
}

As for Pi extensions in yapi, listeners run while yapi keeps drawing, so keys that arrive together pass through them together, and yapi asks providers for suggestions in the background and applies each suggestion as it asks. Each native extension runs in an instance of its own, and the listeners of every instance see input. Completion goes through the providers of one instance, the one that added a provider last. Only the interactive mode runs listeners and providers.

Background work and cancellation

Handlers are async. While one waits for a host operation, other handlers, tool calls and background tasks run. spawn runs a future in the background after the handler that started it returns, like a promise a Pi extension does not await. A background task can report its result with the session.sendMessage request, with "triggerTurn": true to start a turn when the agent is idle.

When the user aborts a run, yapi drops the futures of the extension tools still running in it, which kills the processes they hold. Background tasks keep running until they finish or the extension stops.

A tool that calls Context::aborted gets the abort instead, as a Pi tool’s signal does. The future resolves when the user aborts the run. The tool keeps running to stop its work, and the result it returns becomes the tool’s result, such as the output so far. A tool that has not returned 10 seconds after the abort is dropped. That leaves time to stop a child process with SIGTERM, wait for it and report. Race the future against the work with futures::select! or a small helper, such as race in the countdown example:

#![allow(unused)]
fn main() {
let mut process = Process::spawn(&json!({"command": "make", "args": ["test"]}))?;
let mut output = Vec::new();
loop {
    match race(process.next(), ctx.aborted()).await {
        Ok(Some(ProcessEvent::Stdout(bytes))) => output.extend(bytes),
        Ok(Some(_)) => {}
        Ok(None) => break,
        Err(()) => {
            process.kill("SIGTERM");
            while process.next().await.is_some() {}
            output.extend(b"\n[stopped]");
            break;
        }
    }
}
Ok(ToolResult::text(String::from_utf8_lossy(&output)))
}

Each call into an extension may compute for 60 seconds, not counting time spent waiting on yapi, and each extension may use 1 GiB of memory. The limits apply to each native extension separately.

permission-gate

Asks before dangerous bash commands run: recursive deletes, sudo, and chmod or chown with 777. A todo tool with list, add, toggle and clear actions, and a /todos command that shows the list in a component until Escape closes it. Each result carries the whole list in its details. #![allow(unused)]
fn main() {

            state.next_id = details["nextId"].as_u64().unwrap_or(1);
        }

countdown

A countdown tool that counts down from seconds and shows each second as progress. When the user aborts the run, it stops with its own result, such as Stopped with 7 seconds left, and its details name the call with Context::tool_call_id. Stopping takes cleanup seconds, as stopping a process can. With a cleanup over 10 seconds yapi drops the tool instead. A wait tool ignores aborts, so yapi drops it at once.

#![allow(unused)]
fn main() {
for left in (1..=seconds).rev() {
    ctx.update(&ToolResult::text(format!("{left}...")));
    if race(sleep(1000), ctx.aborted()).await.is_err() {
        sleep(cleanup * 1000).await;
        return Ok(
            ToolResult::text(format!("Stopped with {left} seconds left"))
                .with_details(details),
        );
    }
}
}

race polls two futures until one finishes, so the tool needs no other crate. futures::select! does the same.

Differences from Pi

yapi follows Pi v1.0.0 and behaves like Pi except as listed here. Any other difference is a bug. Please report it.

yapi is tested against Pi itself. 369 end-to-end scenarios compare yapi with output recorded from Pi: terminal screens, JSON event streams, print mode runs and RPC sessions. Settings, credentials and session files round-trip byte for byte. Extensions has the extension and package results.

Roadmap

yapi 0.1 implements the coding agent of Pi 1.0. This page lists the work planned after it. The items have no dates and may change. The issue tracker tracks individual work.

Pi features not yet ported

Some Pi features are missing or incomplete, including highlighted code blocks and LaTeX in Markdown, syntax highlighting in tool output, inline images, prompt cache warming and complete provider objects from extensions. Differences from Pi lists each gap with its issue.

Capability-based sandboxing

In v0.1, every package receives Pi’s default grants: file, process, network and environment access. The plan is to run each package with only the access it needs:

  • A package declares the grants it needs in its own manifest. You approve them, and yapi runs the package in its own instance with only those grants.
  • File grants can be limited to paths and to read-only access, and network grants to hosts.
  • The pi.events bus stays within packages of the same grants unless your settings allow more. A package’s own manifest cannot widen it.
  • Host features that do not check grants today, such as running other tools, reading API keys, the event bus and session actions, will check them.

Security model and sandboxing describes the current model.

Project manifests

A yapi.toml file at a project’s root will list the packages, extensions and skills the project uses. Anyone who checks out the project then installs the same set at the same versions, as Cargo.toml does for a Rust project.

Package registry

A central registry of yapi packages will let manifests name packages and versions instead of npm or git sources.

Stable native extension API

The native extension API is unstable until yapi 1.0. The Rust SDK and host requests may change in any release before then, and extensions may need to be rebuilt. yapi 1.0 will stabilize them. Asynchronous host calls will move to WASI Preview 3 as a new version of the WIT world.

Platforms

Linux and macOS are fully supported, and Windows is best effort. Windows-specific features, such as a PowerShell tool and native console input, will follow once the core is stable.

What each measure means

  • Startup, interactive: time from starting the interactive mode in a 100×40 pseudo-terminal until the footer shows the model.
  • Startup, print mode (to first request byte): wall time from starting -p "hi" until a local listener standing in for the provider receives the first byte of the request. It covers loading settings, credentials, the model catalog and the session, and building the request.
  • Keystroke to paint: time from writing a key into the pseudo-terminal until the character appears on screen, over 200 keystrokes 20 ms apart, in a session whose transcript renders about 10,000 lines.
  • Memory: resident set size (RSS) of the program and its child processes, as ps reports it, 2 s after the first paint or, for the session of turns, 2 s after the last answer.
  • Memory, idle: an interactive start with no session history and no extensions.
  • Memory, 10,000-line session open: the session of the keystroke measure, opened with --session.
  • Memory after 20 turns with tool calls: 20 prompts typed into the editor. A local mock provider answers each with a tool call, alternately read on a 1,000-line file and bash running seq 1 3000, and then with a Markdown answer holding a list and a code block. The mock checks that both programs make the same 40 requests.
  • Memory with 10 small JS extensions: ten TypeScript extensions in the agent directory, each registering a tool, a command and an event handler.
  • Memory with Pi’s example extensions: 57 of the 70 single-file example extensions that ship in Pi’s npm package, loaded together from the agent directory. The rest are left out: five replace the footer, header or editor, where the benchmark looks for the first paint, three start commands, timers or file watchers when a session starts, one commits to the working directory’s repository on exit, and four override a built-in tool that another example also overrides, which Pi refuses to load together.
  • For every measure with extensions, a first start fills the compile caches and is not measured.
  • Install size: yapi’s release executable, which the release profile strips. For Pi, the published npm package and its dependencies installed with --ignore-scripts (121.8 MB, including prebuilt native modules for every platform), plus the Node.js executable it needs (124.8 MB on Linux).

Method

  • Every program runs with a cleared environment, a fresh home and agent directory, PI_OFFLINE=1, and a placeholder Anthropic key pointed at a local listener or mock provider, so no measure touches the network.
  • Startup measures run 20 times per program and memory measures 5 times, alternating between yapi and Pi, so drift on the machine affects both alike. Keystrokes run 200 times per program.
  • Medians are reported because single slow runs come from the machine rather than the program. On the macOS runner, single samples reach 128 ms for yapi’s interactive startup and 444 ms for Pi’s.
  • Pi runs from the same npm install whose size is measured, as its README recommends installing it. The example extensions come from that install too.
  • MB means 10^6 bytes.

Results vary with the machine. Compare yapi and Pi from the same run, not numbers from different machines.

Troubleshooting

Network

yapi honors HTTPS_PROXY, HTTP_PROXY, ALL_PROXY and NO_PROXY, and the httpProxy setting. Certificates are checked against the operating system’s trust store.

--offline, or PI_OFFLINE=1, skips startup network work such as downloading fd and rg.

macOS blocks a downloaded binary

macOS marks an archive downloaded in a browser as quarantined, and Gatekeeper then refuses to open the yapi binary inside it, which Apple has not notarized. The install script, curl and Cargo do not set the mark. Remove it from the unpacked binary:

xattr -d com.apple.quarantine ~/.local/bin/yapi

No models available

yapi found no credentials. Set a provider’s API key or run /login. See Choose a model.

An extension breaks startup

yapi -ne starts without extensions, including the built-in MCP and llama.cpp extensions. yapi config then turns the failing extension off.

Reporting a problem

Run /debug to write the screen, the session’s messages and recent extension output to ~/.yapi/agent/yapi-debug.log. Check it for private data, then attach it to a report on the issue tracker with the output of yapi --version and your operating system.

Contributing

yapi is a Cargo workspace whose crates mirror Pi’s packages. AGENTS.md describes the architecture, the design decisions and the rules for changes. dev/status.md tracks progress and deferred work.

Prerequisites

  • Rust stable. rust-toolchain.toml selects it with Clippy and rustfmt, and rustup installs it on the first build.
  • cargo-deny for the license and advisory check: cargo install --locked cargo-deny.
  • rg, fd and python3 on PATH for the tests.
  • A checkout of Pi v1.0.0 (commit a13d35a) outside this repository. Read the matching Pi source before changing a behavior.
  • Node.js 22.19 or newer, only to record goldens from Pi or compare with Pi live.
  • A WASI SDK and the wasm32-wasip2 Rust target, only to rebuild the JS runtime with cargo xtask js-runtime.

The first build compiles about 420 crates, wasmtime among them, and takes several minutes. Later builds are incremental.

Releasing

  1. Set the new version in [workspace.package] of both Cargo.toml and guest/Cargo.toml. The extension SDK takes the guest workspace’s version, and the Release workflow fails when the two differ from each other or from the tag.
  2. For a new minor or major version, raise the version requirements on yapi-types and yapi-tui in Cargo.toml and guest/yapi-extension-api/Cargo.toml.
  3. Update the versions that the yapi new template, the README and these docs pin. git grep for the old version lists them, such as git grep -n '0\.1\.0'.
  4. Run cargo metadata --format-version 1 >/dev/null in guest to update guest/Cargo.lock, then cargo xtask js-runtime with a WASI SDK. The lock file is an input of yapi-js.wasm.
  5. Add the release’s section to CHANGELOG.md.
  6. Merge, then push the tag v<version>. The Release workflow builds and publishes the binaries and the documentation archive, then publishes yapi-types, yapi-tui and yapi-extension-api to crates.io with trusted publishing, so no token is stored. Each of the three crates has a trusted publisher on crates.io for repository SkymanOne/yapi, workflow release.yml and no environment.
