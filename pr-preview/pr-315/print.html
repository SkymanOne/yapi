yapi

yapi

yapi is a coding agent for the terminal. Given a task and a working folder, it inspects files, runs commands, edits code and works through multi-step tasks. This book covers installing and running yapi, connecting models, customizing it with packages and extensions, and pinning a project’s packages with chest.

How yapi relates to Pi

yapi is a Rust reimplementation of Pi v1.0.0. It uses Pi’s commands, settings, session files, packages and extension API, so yapi import pi brings an existing Pi setup over without conversion. It ships as a single native binary and doesn’t require Node.js.

Get started with yapi

Run your first task covers installation, connecting a model and a first task. Pi users can copy their setup, as Move from Pi to yapi describes. After that:

  • Use yapi in the terminal to attach files, run commands and direct ongoing work.
  • Choose a model and connect a subscription, API key, cloud provider or local model.
  • Manage sessions to resume work or try another approach without losing history.
  • Configure yapi with settings, project instructions, skills and prompt templates.

Customize yapi

Four mechanisms add to what yapi can do:

  • Packages bundle extensions, skills, prompt templates and themes, and install from npm, git or a local path.
  • chest pins a project’s skills, subagents and extensions in a manifest and lock. Skills and subagents work with any agent. Extensions load in yapi, each with the capabilities its entry grants.
  • Model Context Protocol (MCP) servers connect external tools.
  • Extensions add tools, commands, event handlers and interface components. Pi extensions run unchanged, and native extensions are written in Rust. Choose an extension type compares the two.

Automate yapi from other programs

Print mode, JSON mode and remote procedure call (RPC) mode serve scripts, editors and other programs. The formats and protocols are Pi’s, so Pi’s clients work with yapi.

Understand what yapi can access

yapi reads files, edits them and runs commands with your permissions, and it doesn’t ask before each tool call. Extensions run in a WebAssembly sandbox with memory and compute limits. Read Security model and sandboxing before you use yapi with untrusted repositories, packages or unattended automation.

Check compatibility and project status

Differences from Pi lists every known difference. Planned work lists what comes next, and Performance compared with Pi compares startup time, memory and install size. Report problems in the issue tracker.

Run your first task

This guide installs yapi, connects a model and gives yapi its first task in one of your projects. You reach a model through a subscription, an API key or a local server.

Install yapi

On Linux or macOS, run the install script:

curl -fsSL https://raw.githubusercontent.com/SkymanOne/yapi/main/install.sh \
  | sh

The script asks what to install. Press Enter to install yapi and its package manager, chest, in ~/.local/bin. Install yapi covers the other methods. Check the installation:

yapi --version

Start yapi in a project

Start yapi in the folder it should work in:

cd ~/code/my-project
yapi

yapi uses the working folder to find files, project instructions and configuration, and to group saved sessions.

Choose a model

Run /login, choose a provider and follow the prompts to sign in with a subscription or save an API key. Run /model to choose another model.

yapi also reads API keys from the environment, such as ANTHROPIC_API_KEY. Choose a model lists every provider.

Give yapi a task

Type a task and press Enter. yapi shows each file it reads, each command it runs and each edit it makes. It doesn’t ask before each tool call. For example:

Explain how requests flow through src/server.rs
Find why `cargo test` fails and fix it
@Cargo.toml Which dependencies are outdated?
!git status

@path attaches a file. !command runs a shell command and sends its output to the model, and !!command runs it without sending the output. Press Escape to stop the agent and Ctrl+C twice to quit.

Review the changes when yapi finishes. Keep important work under version control, and use a container for untrusted or unattended work, as Security model and sandboxing explains.

Continue a session later

yapi saves sessions automatically. To resume the most recent session in a folder, run:

yapi -c

Use /resume to choose another session. Manage sessions covers the rest.

Install yapi

Releases ship two executables: yapi and chest, the package manager for skills, subagents and extensions. chest also works with other agents and without yapi, so every method on this page installs both or either one alone. This page covers the install script, cargo-binstall, release archives and building from source, then the documentation yapi reads, upgrades and uninstalling.

Releases include builds for Linux and macOS on x86_64 and arm64, and other platforms can build yapi from source. yapi fully supports Linux and macOS. Windows support is best effort.

Run the install script

The install script installs both executables, or one of them, with one command:

curl -fsSL https://raw.githubusercontent.com/SkymanOne/yapi/main/install.sh \
  | sh

The script downloads the latest release for your system and verifies its SHA-256 checksum. In a terminal, it asks what to install:

┌   yapi installer
│
◆  What to install?
│  ● yapi and chest (the coding agent and its package manager)
│  ○ yapi only
│  ○ chest only
└

Move with ↑ and ↓ and press Enter. Enter alone installs both, and Ctrl+C cancels. When the terminal can’t read single keys, such as with TERM=dumb, the script asks for 1, 2 or 3 instead. Set NO_COLOR to turn off colors.

The script puts the executables in ~/.local/bin, and with yapi it also installs the documentation for the model. Without a terminal, such as in CI, it installs both without asking.

OptionVariableEffect
--only <name>YAPI_INSTALL_ONLYInstall yapi, chest or both without asking
--version <tag>YAPI_VERSIONInstall that release, such as v0.4.2
--to <dir>YAPI_INSTALL_DIRInstall into <dir>
--from-sourceYAPI_FROM_SOURCE=1Build the release with Cargo instead of downloading it, as Build from source shows
--no-docsYAPI_NO_DOCS=1Skip the documentation for the model

Pass options after sh -s --. This installs chest alone, such as for another agent:

curl -fsSL https://raw.githubusercontent.com/SkymanOne/yapi/main/install.sh \
  | sh -s -- --only chest

This installs both from v0.4.2 into /usr/local/bin, without the menu:

curl -fsSL https://raw.githubusercontent.com/SkymanOne/yapi/main/install.sh \
  | sh -s -- --only both --version v0.4.2 --to /usr/local/bin

Install with cargo-binstall

cargo-binstall installs the release executables into ~/.cargo/bin. The first command installs yapi, and the second installs chest from its crate on crates.io, chest-cli. Run one or both:

cargo binstall --git https://github.com/SkymanOne/yapi yapi
cargo binstall chest-cli

Keep --git for yapi, because the yapi crate on crates.io is an unrelated project. cargo-binstall installs the yapi release that the manifest on main names. If it reports that this release doesn’t exist, use the install script.

Install from a release archive

Each release has a yapi-<target>.tar.gz archive per platform, with a .sha256 checksum. The archive holds yapi, chest and their license files.

TargetSystems
x86_64-unknown-linux-gnuLinux on x86_64 with glibc 2.35 or newer, such as Ubuntu 22.04, Debian 12 and Fedora 36
aarch64-unknown-linux-gnuLinux on arm64 with glibc 2.35 or newer
x86_64-apple-darwinmacOS on Intel
aarch64-apple-darwinmacOS on Apple silicon

Set target to your system’s target from the table. These commands download its archive, verify it and unpack yapi and chest into ~/.local/bin, or any folder on PATH:

target=x86_64-unknown-linux-gnu
url=https://github.com/SkymanOne/yapi/releases/latest/download
curl -fsSLO "$url/yapi-$target.tar.gz"
curl -fsSLO "$url/yapi-$target.tar.gz.sha256"
sha256sum -c "yapi-$target.tar.gz.sha256"
tar xzf "yapi-$target.tar.gz" -C ~/.local/bin yapi chest

To adapt the commands:

  • To install one executable, end the tar command with only yapi or only chest.
  • On macOS, verify with shasum -a 256 -c.
  • For a specific release, replace latest/download with download/<tag>.
  • With an older glibc, or with musl such as Alpine, build from source instead.

If macOS refuses to open a binary downloaded in a browser, see macOS blocks a downloaded binary.

Build from source

yapi builds with Rust 1.99 or newer, and chest with Rust 1.91 or newer. Install Rust with rustup, then build with the install script or with Cargo.

With --from-source, the install script builds the latest release’s tag with Cargo, or the tag --version names, and never the main branch. Then it installs the executables in ~/.local/bin, and the documentation for the model with yapi. The first command builds both, the second yapi alone and the third chest alone. Run one:

script=https://raw.githubusercontent.com/SkymanOne/yapi/main/install.sh
curl -fsSL "$script" | sh -s -- --from-source --only both
curl -fsSL "$script" | sh -s -- --from-source --only yapi
curl -fsSL "$script" | sh -s -- --from-source --only chest

Cargo builds chest from its crate on crates.io:

cargo install --locked chest-cli

To build from the repository instead, name a release’s tag. The first command below builds yapi, and the second builds chest from its crate, chest-cli. Run one or both:

repo=https://github.com/SkymanOne/yapi
cargo install --locked --git "$repo" --tag v0.4.2 yapi
cargo install --locked --git "$repo" --tag v0.4.2 chest-cli

Cargo installs the executables in ~/.cargo/bin. Leave out --tag to build the latest commit on main.

To build from a clone, run cargo install --locked --path crates/yapi in it, or --path crates/chest for chest. If Cargo reports that rustc is too old, run rustup update.

Check the installation

Each executable prints its version. yapi’s version matches the release tag, such as 0.4.2 for v0.4.2. chest has a version number of its own. Run the line for each one you installed:

yapi --version
chest --version

Documentation for the model

yapi reads its own documentation to answer questions about its features. The documentation holds these pages and Pi’s docs and examples, which describe the extension API. Each release publishes it as yapi-docs.tar.gz, which goes to ~/.yapi/agent/docs, or docs in YAPI_CODING_AGENT_DIR when that’s set.

The install script installs the documentation with yapi, and skips it when it installs chest alone. With any other method, yapi downloads it in the background on first start. Either way, yapi verifies the archive against its checksum, and the archive replaces the previous copy. YAPI_NO_DOCS=1, --offline and PI_OFFLINE=1 turn the download off.

Until a copy for its own version is in place, yapi points the model to the online documentation. Pi’s pages use Pi’s names, such as ~/.pi/agent, and Names that change lists yapi’s.

To install the documentation by hand, such as on a machine that runs offline:

url=https://github.com/SkymanOne/yapi/releases/latest/download
mkdir -p ~/.yapi/agent/docs
curl -fsSL "$url/yapi-docs.tar.gz" | tar xzf - -C ~/.yapi/agent/docs

For an older yapi, replace latest/download with download/v<version>, where <version> is what yapi --version prints. yapi replaces these files on upgrade, so keep your own notes elsewhere.

Upgrade yapi

yapi doesn’t update itself. yapi update prints how to upgrade, yapi update --extensions updates packages and yapi update --models updates model catalogs. Upgrade yapi and chest the same way you installed them:

Installed withUpgrade
Install scriptRun the script again and make the same choice, with --from-source if you built from source. From another script, pass the same --only, because without a terminal it installs both.
cargo-binstallRun the same cargo binstall commands again.
Release archiveUnpack the executables you installed from the new archive over the old ones.
CargoRun cargo install --locked chest-cli again for chest from crates.io. Run the --git commands again with the new release’s tag.

Upgrades keep your settings, credentials, sessions and packages.

In the terminal, yapi checks at startup for a newer release and for package updates, and shows a notice when it finds one. PI_SKIP_VERSION_CHECK=1 turns off the release check. --offline and PI_OFFLINE=1 turn off both.

YAPI_RELEASES_URL points the install script, the release check and the documentation download at another releases page, such as a mirror. It defaults to https://github.com/SkymanOne/yapi/releases.

Uninstall yapi

How you remove the binaries depends on how you installed them:

  • Install script or release archive: delete ~/.local/bin/yapi, ~/.local/bin/chest or both, or the same files in the folder you chose. This also applies to builds with --from-source.
  • cargo-binstall or Cargo: run cargo uninstall yapi to remove yapi, and cargo uninstall chest-cli to remove chest, from crates.io or the repository.

To remove settings, credentials, sessions, packages and caches as well, delete ~/.yapi, or YAPI_CODING_AGENT_DIR when set, and each project’s .yapi folder. chest keeps its global manifest, store and records in ~/.chest.

Move from Pi to yapi

yapi reads Pi’s formats but keeps its own folders, so the two never write the same files. yapi import pi copies an existing Pi setup into yapi’s folders. This page covers what the import copies and leaves out, how to move project packages to chest, and which names change.

Copy a Pi setup

To copy an existing Pi setup, run:

yapi import pi

The command copies Pi’s agent folder, ~/.pi/agent or PI_CODING_AGENT_DIR, into yapi’s. It also copies the current project’s .pi folder into .yapi. From the agent folder, it copies:

  • settings, API keys, models, key bindings and Model Context Protocol (MCP) servers
  • trust decisions
  • the global AGENTS.md or CLAUDE.md, SYSTEM.md and APPEND_SYSTEM.md
  • sessions, prompt templates, skills, themes, extensions and packages

The import keeps every file and package yapi already has, except a settings.json that holds only the version yapi recorded on first start. When yapi keeps its settings in settings.toml, the import skips Pi’s settings.json and says so. Copy the settings you want into settings.toml by hand.

After the import, yapi and Pi work side by side, and each opens the other’s session files.

Sign in again after the import

The import doesn’t copy subscription sign-ins or MCP server sign-ins. Providers can replace the refresh token on every refresh and reject the old one, so a copy would make yapi and Pi sign each other out.

The command lists the providers and servers it left out. Sign in to them again in yapi with /login, or with /mcp login for MCP servers.

Move project packages to chest

To move a project’s packages from .yapi/settings.json into a manifest with a lock, run chest import --settings in the project. It writes an extension entry for each package with capabilities = ["all"], the access Pi gives packages, and prints the yapi remove -l command for each one.

Narrow the capabilities, run chest install, then run the yapi remove -l commands it printed. Import packages from settings.json covers the details.

yapi renames its folders, two environment variables and its own commands:

Use yapi in the terminal

Interactive mode is yapi’s terminal interface. This page covers entering prompts, following and redirecting the work, the default keys, slash commands, shell commands and the two display modes. Run yapi from the folder to work in. To install yapi and choose a model first, follow Run your first task.

The transcript shows your prompts, the model’s responses, tool calls and their results. Prompts and commands go in the editor at the bottom. The footer shows the folder, the model, context usage and cost.

Enter a prompt

Type a request and press Enter to send it. Shift+Enter adds a line, and Ctrl+G opens the prompt in $EDITOR. The editor also takes files and history:

  • @path attaches a file. Tab completes the path.
  • Ctrl+V pastes text, an image, or on macOS the paths of copied files. yapi saves a pasted image to a temporary file and puts its path in the editor.
  • Up recalls earlier prompts.

A prompt or command that you send while extensions start, or while an extension command runs, waits until they finish. yapi then sends it in the order you sent it.

Follow the agent’s work

yapi shows each tool call as it runs. Ctrl+O expands or collapses tool output, and Ctrl+T shows or hides thinking.

Messages show Markdown with LaTeX math and Mermaid diagrams. “Mermaid diagrams” in /settings draws diagrams while a message streams, only once it’s complete, or never.

Choose a display mode

yapi draws in fullscreen mode by default. Regular mode keeps the transcript in the terminal’s scrollback instead. Switch with /settings or --tui-mode regular.

In fullscreen mode, yapi handles the mouse:

  • The wheel scrolls the transcript. Hold Alt to scroll five times as far. “Fullscreen wheel scrolling” in /settings sets a fixed number of lines per step.
  • Drag to select text. A double click selects a word or path, and a triple click selects a line. Releasing the button copies the selection. With “Fullscreen copy on select” off, press Ctrl+X to copy it.
  • A click on a tool call, thinking, a skill or a summary expands or collapses it. Ctrl+O and Ctrl+T still set every item at once.
  • A click on a web or mail link opens it, and a click on a file link shows the file in its folder. Other links don’t open, so a click never starts a program. See Hyperlinks in the terminal.
  • A click in the editor, a list or a dialog moves the cursor or chooses the item.
  • Drag the scrollbar’s thumb, or click its track to jump. With “Fullscreen scrollbar” set to auto, pointing at the scrollbar shows it, except inside tmux, Zellij and GNU Screen.

Choose a model

yapi supports Pi’s providers and models, from the same built-in catalog. This page covers signing in, API keys, cloud and local providers, selecting a model, adding providers and handing credentials to other tools.

Sign in with a subscription

Run /login and choose “Sign in with an account” to use a Claude Pro or Max, ChatGPT Plus or Pro, GitHub Copilot, Kimi For Coding, Meta, SuperGrok or X Premium account, or to create an OpenRouter key. yapi opens the browser sign-in, or shows a device code, and refreshes the token when it expires.

“Sign in with Radius” signs in to Pi’s Radius gateway, whose models come from the gateway’s own catalog. Providers that extensions register can add their own sign-ins. /logout removes a stored credential.

Use a cloud provider

Amazon Bedrock, Google Vertex AI and Cloudflare use their platform’s credentials:

  • Amazon Bedrock: reads AWS_BEARER_TOKEN_BEDROCK, or Amazon Web Services (AWS) credentials from the environment, ~/.aws profiles (including single sign-on and assumed roles), container credentials or instance metadata. It takes the region from AWS_REGION or the profile.

/login can store these settings in auth.json instead. With ANTHROPIC_FEDERATION_RULE_ID and the related variables set, Anthropic requests use workload identity federation instead of a key.

Run local models

yapi supports the llama.cpp router server. Start llama-server in router mode, without --model:

llama-server --models-dir ~/models --no-models-autoload --jinja \
  --host 127.0.0.1 --port 8080

Run /login llama.cpp and enter the server URL and an optional API key, or set LLAMA_BASE_URL and LLAMA_API_KEY. /llama loads and unloads the server’s models and downloads new ones from Hugging Face. Loaded models appear in /model. Pi’s llama.cpp guide covers the server options.

To remove the provider and /llama, disable llama.cpp in yapi config.

Select a model

--list-models searches the catalog, and --model takes an exact model or a pattern, with an optional thinking level after :. --models sets the models that Ctrl+P cycles through:

yapi --list-models sonnet
yapi --model anthropic/claude-sonnet-4-5
yapi --model sonnet:high
yapi --models "sonnet,gpt-5*"

Inside yapi, /model or Ctrl+L opens the model selector, Ctrl+P cycles through models, and Shift+Tab cycles the thinking level.

Add providers and models

Add providers, models and overrides to ~/.yapi/agent/models.json. Pi’s models and custom provider documentation describe the format. Extensions can also register providers, including ones with their own wire API.

Update the model catalog

Pi publishes catalog updates between releases. yapi fetches them for the providers you’ve configured: at startup, when the model selector opens, after /login and with yapi update --models. It keeps them in ~/.yapi/agent/models-store.json for offline use. --offline, or setting PI_OFFLINE, turns off the automatic fetches, but not yapi update --models.

Use classifier and image models

The catalog also lists classifiers, which answer typed questions about JSON data, and image models on OpenRouter. Codemode scripts run them through the models global, and extensions through ctx.modelRegistry.classify() and generateImages().

Give credentials to other tools

yapi auth gives scripts a credential without starting a session. check reports whether a provider is ready, and the print- commands print its API key or bearer token:

yapi auth check --provider anthropic --json
yapi auth print-api-key --provider openai
yapi auth print-bearer-token --provider openai-codex --min-expiry 30m

print-bearer-token refreshes a token that expires within --min-expiry, which is 30 minutes by default and at least 5 minutes. It fails when the refreshed token doesn’t last that long.

Manage sessions

yapi saves every conversation as a JSON Lines (JSONL) file under ~/.yapi/agent/sessions/, grouped by project. Pi and yapi open each other’s sessions. This page covers resuming, branching, compacting, keeping the prompt cache warm, and exporting and importing sessions.

Continue earlier work

These flags choose which session a run uses, or whether it saves one:

yapi -c                      # continue the last session in this folder
yapi -r                      # pick a session to resume
yapi --session 3f2a          # open a session by file or id prefix
yapi --fork 3f2a             # copy a session into a new one
yapi --no-session            # don't save this run

Inside yapi, /resume opens the session picker, /new starts a fresh session and /name names the current one.

Branch a session

A session is a tree. When you go back to an earlier message, yapi keeps the abandoned branch. Three commands work with branches:

  • /tree shows every branch and jumps to any earlier point. By default, pressing Escape twice on an empty editor opens it too. The doubleEscapeAction setting changes this to fork or none.
  • /fork starts a new session from an earlier message.
  • /clone duplicates the current session.

Compact a long session

Long sessions fill the model’s context window. yapi summarizes older messages automatically before that happens. /compact runs it on demand, and /settings turns automatic compaction off.

Keep the prompt cache warm

Providers keep a cached prompt for a limited time, such as 5 minutes with Anthropic’s default retention. yapi can resend the latest request shortly before the cache expires, when it expects that to save money. The cacheWarming setting, read from global settings only, picks when:

  • streaming: the default, warms while the agent works
  • idle: also warms between runs
  • off: never warms

/session shows the next decision and the tokens billed again after cache misses. “Cache miss notices” in /settings shows refreshes and costly misses in the transcript.

Export and import sessions

/export writes the session to a standalone HTML file. yapi --export <file>.jsonl [output.html] does the same for a session file from the command line. /export <path>.jsonl writes the current branch as a new session file, without the other branches.

/import <path>.jsonl copies a session file into the project’s session folder and resumes it. When the session’s working folder no longer exists, yapi asks whether to resume it in the current folder instead.

Security model and sandboxing

yapi reads files, edits them and runs commands on your machine. This page describes what yapi protects, what it leaves to the operating system, how yapi isolates extensions and which grants they need, and how project trust works.

What runs with your permissions

yapi runs with your permissions. It doesn’t sandbox its built-in tools read, bash, edit and write, and it doesn’t ask for approval before each tool call. A command the model runs can read or change any file, and reach any service, that you can.

Treat the commands and code the model generates as untrusted. Files, comments and command output that the model reads can steer it through prompt injection. Reviewing the transcript and granting project trust don’t create a security boundary.

  • Keep important work under version control.

How the extension sandbox works

Every extension runs in a WebAssembly instance hosted by Wasmtime, separate from yapi’s own memory. The sandbox limits what extension code can do directly. It doesn’t restrict the built-in tools, child processes or MCP servers.

Instances and limits

An instance is a trust domain. Pi extensions with the same grants and event policy share one QuickJS-NG instance, because the host can’t enforce grants between packages that share a JavaScript realm. Each extra instance costs a thread and has its own memory limit of 1 GiB.

Packages from yapi install share one instance, and chest extensions with other grants or another event policy run in instances of their own. Each native extension gets an instance of its own, and codemode gets a fresh instance with no grants for every script.

Each instance runs under these limits:

  • Compute per call: 60s, not counting time spent waiting on yapi
  • Compute while loading: 10s per call while an instance starts and while it loads or reloads its extensions
  • Memory: 1 GiB for each extension instance, and 384 MiB for each codemode instance

An instance runs one call at a time, so a long computation in one Pi extension delays the other Pi extensions. When an instance traps, for example by exceeding a limit, yapi restarts it and reloads its extensions. If reloading them traps again, the instance stays stopped, and each later call to it fails after one more attempt to restart it.

How yapi enforces grants

The host checks an extension’s file, process, network, environment and session access against its grants, and routes pi.events by them, as Agent sessions and events describes. A chest extension receives only the capabilities its manifest entry grants, and the capability table lists what each one allows.

A process grant amounts to all the others in practice. The host checks each grant separately, but a process an extension starts runs as you, outside the sandbox, and inherits yapi’s environment, including API keys. A subagent is such a process: a full yapi with your installed packages.

Without the file grant, an extension loads the files of the packages that share its instance, and their dependencies, and nothing else. yapi refuses a path that leads out of a package through a symlink, and a path with . or .. in it.

Every extension file yapi finds in a chest package, including an index.ts or index.js that no manifest lists, runs with its entry’s capabilities. The file keeps them when -e or a project folder loads it too, even through a symlink, and yapi warns about it. A file that yapi loads for a chest package but can’t match to an entry runs with no capabilities, with a warning.

chest refuses to install an extension whose folder is or holds the project, the home folder or the agent folder, because it could load any file there. yapi doesn’t load such an entry, locked or not, nor a global entry whose folder holds the project yapi runs in. In two more cases, files run with no capabilities:

  • Extension files of a refused entry: they run with no capabilities when Pi’s discovery, settings or -e load them. Other files in its folder keep the grants of their own source.
  • Files of an entry with a stale or missing lock: every one of them runs with no capabilities when something else loads it.

A file that runs with no capabilities in either case loads no other file as a module. When two manifests give the same file, it runs with only what both allow.

Grants for servers, models and tools

Registering servers, reading credentials and calling models each need a specific grant. An extension can register a stdio MCP server only with the process grant, and an HTTP server only with the network grant.

Reading a provider’s credentials with ctx.modelRegistry.getProviderAuth, getApiKey, getApiKeyForProvider or getApiKeyAndHeaders needs the network grant. So does calling a model with complete, stream, streamSimple, classify or generateImages. Without the network grant, ctx.modelRegistry.refresh refreshes model lists offline.

Running a tool needs grants too, whether an extension creates a built-in tool such as createBashTool or calls a tool with ctx.executeTool:

  • The built-in read, write, edit and ls tools need the file grant, and bash needs the process grant.
  • The built-in grep and find tools need the file, process and network grants, because they run ripgrep and fd and download them when they’re missing.
  • Any other tool needs every grant, because yapi can’t tell what it reaches. This covers another extension’s tool, a tool that replaces a built-in one, and an MCP tool.

A codemode script that an extension runs sees only the tools that the extension’s grants allow. It calls models only with the network grant, and keeps what it stores only with the session grant.

What the session grant covers

The session grant covers actions that start, steer or stop turns, or change the session, its files or the model’s setup:

  • pi.sendMessage, sendUserMessage, appendEntry, setSessionName, setLabel, setModel, setThinkingLevel and setActiveTools
  • writes through ctx.sessionManager, and the system prompt options that a command edits
  • ctx.compact, abort and shutdown, and a command’s newSession, fork, navigateTree, switchSession and reload
  • text that a custom editor submits
  • the editor actions that interrupt, exit or suspend yapi, clear the editor, cycle the model or the thinking level, show or hide thinking, restore queued messages, or start a new session

Without the file grant, switchSession and the parentSession of newSession accept only session files in the session folder. Holding a file with withFileMutationQueue needs the file grant, because the model’s edit and write tools wait while an extension holds it. Pi has no session grant.

Requests that need no grant or every grant

Some requests need no grant:

  • reading the session, such as its entries, name and model
  • dialogs, widgets and notifications
  • the editor actions that expand tool output, copy the last message, or open the model, tree, fork or resume selector, where you make the choice
  • copyToClipboard, which writes the system clipboard. A person may paste what it copies into a terminal or another program, so treat text an extension copies as untrusted, as you would text from a web page.

Some actions need every grant, because they reach outside the sandbox or act with yapi’s own access:

  • registering a provider or a wire API, because a provider’s replies drive the agent’s tools and its requests carry your credentials
  • custom editor text that starts with ! or /, after any leading spaces, because it runs a shell or slash command
  • listening to raw terminal input with ctx.ui.onTerminalInput, or adding an autocomplete provider with ctx.ui.addAutocompleteProvider, because either can turn what you type into a shell or slash command. Without every grant, both calls throw in a Pi extension and do nothing in a native one.
  • the editor actions that open the external editor, paste from the clipboard, or submit the editor’s text as a follow-up
  • any request or editor action that yapi doesn’t know, so a new one stays denied until yapi classifies it

A provider or wire API that an extension without every grant registers stays unused, and yapi logs a warning for each one in the extension output.

A custom editor that passes a key on to extension shortcuts runs only extension shortcuts, never yapi’s own key actions, which go through the editor actions above. Each shortcut runs under the grants of the extension that registered it, as a pi.events listener does.

Event handler results

yapi applies what an extension’s event handlers return only within the extension’s grants. Any change to what the model sees needs the session grant:

  • A tool_call handler can always block a call, but the reason it gives reaches the model only with the session grant. Without it, the model reads “Tool execution was blocked”.
  • A tool_call handler changes the call’s input only with the session grant and the grants that would let it run that tool itself.
  • Results that add or change messages, context, user input, the system prompt or its options, provider requests, tool results, tool descriptions, compaction or tree summaries, or entries staged at the end of a turn need the session grant. So do results that start another turn or keep warming the prompt cache.
  • Results that only cancel, block or stop need no grant, such as cancelling a compaction, a session switch or a fork, or stopping a run or cache warming. An input handler that handles the input itself and a user_bash handler that fails a ! command need no grant either, because they stop work and show text only to you, not to the model.
  • A user_bash handler that runs a ! command through its own operations, or answers it with its own result, needs every grant, because the extension then decides what runs and what you see as your shell’s output.
  • The skill, prompt and theme paths that a resources_discover handler names need the session and file grants.

A result that yapi ignores counts as no result, so it never replaces what an extension with the grant returned for the same event. yapi logs a warning in the extension output for each kind of result it ignores, once for each extension, with what it ignored, such as the reason of a block.

The before_provider_request and before_provider_headers events carry a request’s body and headers, which can hold your credentials, so they reach only extensions with the network grant.

Agent sessions and events

yapi never runs an agent session inside an extension’s instance, because that session would run tools and use credentials outside the extension’s grants. Subagents run as separate yapi processes instead.

Pi’s exports that read auth.json, write trust.json or settings.json, or write session files directly throw in extensions, so extensions reach credentials, project trust, settings and sessions through the host. Until yapi can limit file grants to paths, an extension with the file grant can still open these files itself, as in Pi.

Extensions share Pi’s pi.events bus. Between extensions with different grants, sharing leaks access both ways: an extension that acts on events lets the sender borrow its grants, and an extension that listens learns what the sender emits.

yapi routes each event by the grants and the event policy of the extensions it runs in. An event reaches another extension when both have identical grants, or when the sender’s policy lets it send the channel and the receiver’s policy lets it hear it.

Packages from yapi install, and chest entries without an events key, get the shared policy, * both ways, so they hear every other extension’s events, as in Pi. A chest entry’s events key narrows its own policy, as the event bus reference describes.

When routing keeps an event from an extension that listens on its channel, yapi logs a warning in the extension output, once per channel and session. An extension misses events explains the warning.

Project trust

Some files in a project can change how yapi behaves and can run code. Until you trust the project, yapi loads none of them, and no project extension runs:

  • settings.json or settings.toml, mcp.json, extensions, skills, prompts, themes, SYSTEM.md and APPEND_SYSTEM.md in the project’s .yapi folder
  • an .agents/skills folder in the project or a parent folder
  • a chest manifest that installs anything

The first time interactive mode starts in a project that has them, yapi asks whether to trust it. Print, JSON and remote procedure call (RPC) modes never ask, and treat the project as untrusted unless a decision applies:

  • yapi saves the decision in ~/.yapi/agent/trust.json. /trust changes it later.
  • If yapi can’t read trust.json, or it isn’t a JSON object, yapi reports the error and doesn’t start in a project that needs trust, as Pi does, unless --approve or --no-approve decides. It never overwrites that file.
  • --approve and --no-approve decide for one run.
  • "defaultProjectTrust" in global settings set to "always" or "never" decides without asking.

AGENTS.md and CLAUDE.md load whether or not you trust the project. Treat their contents as untrusted input as well.

Use the project of another folder

--project-dir <dir> takes the project from another folder, as if yapi had started there. yapi loads that folder’s .yapi files and the AGENTS.md or CLAUDE.md of that folder and its parents, and applies trust to that folder, including --approve and --no-approve. The working folder’s own .yapi folder doesn’t load.

Tools, the session and extensions’ ctx.cwd stay in the working folder. A native extension finds the project folder with project_dir(). Subagents use the flag to work in one folder with their parent’s project.

Report a vulnerability

Report vulnerabilities privately, as SECURITY.md describes.

Automate yapi

yapi runs without its interface for scripts, editors and other programs. This page covers print mode, JSON mode and remote procedure call (RPC) mode, and the flags that matter when another program drives yapi. The formats and protocols are Pi’s, so Pi’s clients work with yapi.

Answer once with print mode

-p sends one message, prints the answer and exits. These three runs take a prompt, piped input and attached files:

yapi -p "Summarize the open TODOs in src/"
git diff | yapi -p "Write a commit message for this diff"
yapi -p @report.md @chart.png "What does the chart show?"

Piped input becomes part of the first message, and @path attaches files and images.

Stream events with JSON mode

--mode json prints one JSON event per line for the whole run: message updates, tool calls, tool results and the final state. Pi’s JSON documentation describes the events.

yapi --mode json -p "List the crates in this workspace"

Drive yapi with RPC mode

--mode rpc keeps yapi running and reads commands from stdin, one JSON object per line. Responses and events go to stdout. Clients can prompt, steer, abort, switch models and sessions, and answer extension dialogs.

Pi’s RPC documentation lists the commands, and Pi’s RpcClient works with yapi. This starts an RPC session that saves nothing:

yapi --mode rpc --no-session

How yapi writes the file

/settings, yapi config, yapi install and the other commands that change settings keep your comments and layout. They rewrite only keys whose values differ, add new keys and delete removed ones. Comments stay with their key or list entry, and a removed entry takes its comments along. A [[packages]] array of tables becomes an inline array once an entry is a plain source string, such as after yapi install npm:@acme/pi-tools.

Switch to TOML

With yapi closed, write settings.toml with your settings, then delete settings.json. A yapi that’s still running keeps writing the file it loaded, which can bring settings.json back beside the new file.

Project packages from chest

yapi loads the project packages that two chest manifests list:

  • chest.toml in the project folder, or the manifest that CHEST_MANIFEST names, such as chest.dev.toml
  • ~/.chest/chest.toml, which lists packages for every project

A project manifest that installs anything loads only in a trusted project.

Project instructions

yapi reads one instruction file from the working folder and from each parent folder, and adds them to the system prompt. In each folder it takes the first of AGENTS.override.md, AGENTS.md and CLAUDE.md that exists. In a git worktree inside its main checkout, such as .worktrees/feature, the worktree’s own file replaces the main checkout’s file of the same name.

Skills and prompt templates

Skills follow the Agent Skills specification. Each skill is a folder with a SKILL.md file. yapi lists every skill’s name and description in the system prompt, and the model reads the full instructions when a task calls for them. /skill:name loads one directly.

Prompt templates are Markdown files that become slash commands. Save this as ~/.yapi/agent/prompts/review.md:

---
description: Review staged git changes
argument-hint: "[focus]"
---
Review the staged changes. Focus on ${1:-correctness and error handling}.

/review then sends the prompt, and /review concurrency fills in the focus. Pi’s prompt template documentation lists every argument form.

Choose a theme

Choose a theme in /settings or with "theme" in settings. --use-theme <name> applies one for a single run. Theme files use Pi’s JSON format, described in Pi’s theme documentation.

Change key bindings

~/.yapi/agent/keybindings.json changes the keys. Pi’s key binding documentation lists the format and every action. /hotkeys shows the bindings in effect.

How yapi prepares images for the model

yapi prepares images in prompts, @path arguments and tool results before they reach the model:

  • yapi converts BMP, TIFF, ICO, PNM, HDR, DDS and farbfeld images to PNG. This applies to images that arrive with a MIME type: remote procedure call (RPC) and SDK prompts, tool results and the clipboard. @path arguments and the read tool only recognize PNG, JPEG, GIF, WebP and BMP files, so they read other formats as text.
  • With "images": {"autoResize": true}, the default, yapi scales larger images down to fit 2000×2000 pixels and 4.5 MiB as base64, or the model’s own limits. It may send a scaled image as JPEG, with a note that gives the model its original size.
  • yapi leaves out a prompt or read image that it can’t convert or make fit, with a note that says so. A tool result keeps its original image unchanged.
  • "images": {"blockImages": true} keeps all images from the model.

Both settings are also in /settings.

Show images in the terminal

In kitty, Ghostty, WezTerm, Warp, iTerm2 and Herdr, tool results show their images below the tool. Kitty’s protocol takes PNG only, so yapi shows other formats as PNG copies. Other terminals, tmux and screen show a note with the image’s type and size instead. In fullscreen mode, iTerm2 also shows the note, as in Pi.

"terminal": {"showImages": false} turns images off, and "imageWidthCells" sets their preferred width in cells, 60 by default. Both are in /settings when the terminal shows images. Set "terminal": {"images": "kitty"}, "iterm2" or false to override the detection. The PI_IMAGE_PROTOCOL environment variable, kitty, iterm2 or none, does the same, and the setting takes precedence.

Hyperlinks in the terminal

In a terminal that supports hyperlinks, Markdown links show only their text, and the paths in read, write, edit and ls calls link to their files. In other terminals, a Markdown link shows its URL after its text.

yapi detects hyperlink support in common terminals, such as iTerm2, Ghostty, kitty, WezTerm and VS Code, and asks tmux whether it passes hyperlinks on. Set "terminal": {"hyperlinks": true} or false to override the detection. The PI_HYPERLINKS environment variable, 1 or 0, does the same, and the setting takes precedence.

Terminal colors

Themes use 24-bit color in terminals that support it, such as iTerm2, Ghostty, kitty, WezTerm, VS Code and JetBrains IDEs, or when COLORTERM is truecolor or 24bit. Elsewhere, and in tmux or screen unless COLORTERM says so, they use 256 colors. Set "terminal": {"trueColor": true} or false to override the detection. The PI_TRUE_COLOR environment variable, 1 or 0, does the same, and the setting takes precedence.

Use packages

A package bundles extensions, skills, prompt templates and themes. yapi installs Pi packages from npm, git or a local folder, with no Node.js required. This page covers installing, trying and turning off packages, pinning a project’s packages with chest, package manifests and yapi’s built-in npm client.

Install and manage packages

yapi install takes an npm or git source, a local folder or a single native extension, and -l installs it for the current project only. yapi list, yapi update --extensions and yapi remove list, update and remove what’s installed:

yapi install npm:@your_scope/your_package
yapi install git:github.com/your_user/your_repo
yapi install ./your_package -l
yapi install ./shout.wasm
yapi list
yapi update --extensions
yapi remove npm:@your_scope/your_package

yapi records installed packages in settings.json. -l installs into the project’s .yapi folder and records the package in .yapi/settings.json, which loads only in a trusted project. Local folders and files load in place, without a copy.

At startup and on /reload, yapi installs configured packages that are missing. It also reinstalls npm packages whose installed version is outside their configured range or whose install was interrupted.

Packages can run code and can hold skills that instruct the model to run programs. Review a third-party package before you install it.

yapi list shows each package with its install location. A tag after the source shows its extension kinds: [npm] for JavaScript or TypeScript, [wasm] for native, or [npm, wasm] for both. Packages without extensions, and packages not installed yet, have no tag.

User packages:
  npm:pi-mcp-adapter [npm]
    /home/you/.yapi/agent/npm/node_modules/pi-mcp-adapter
  /home/you/extensions/shout.wasm [wasm]
    /home/you/extensions/shout.wasm

yapi update --extensions moves each npm package to the newest version its source’s range allows, unless the source names an exact version. It moves each git package to the latest commit of its branch or ref.

The npm and git folders each hold a .gitignore that keeps installed packages out of a project’s repository. At startup, the terminal interface checks npm packages and git packages without a ref for updates, and lists those that have one.

Try a package for one run

-e loads a package for one run without adding it to settings:

yapi -e npm:@your_scope/your_package
yapi -e git:github.com/your_user/your_repo

yapi installs these into ~/.yapi/agent/tmp/extensions and reuses them on later runs. It installs an npm package again when its version no longer matches the source’s range, and updates a git source without a ref on each run. With --offline or PI_OFFLINE, yapi installs and updates nothing, and skips a source that isn’t installed yet.

Turn resources on and off

yapi config lists every extension, skill, prompt template and theme from your packages, settings and folders. Space toggles one, and yapi saves the choice in settings.json, or in settings.toml when that’s the folder’s file. Tab switches between global settings and the current project, and yapi config -l starts with the project. In the Global Resources view, ctrl+o keeps the selected item in project-only runs.

Before it opens, yapi config installs the packages that are missing or outside their range, unless PI_OFFLINE is set. If an install fails, it prints the error and exits.

To run with only a project’s packages and none of your global ones, start yapi with --project-only. Run yapi with only the project’s packages covers the mode.

Project packages with chest

chest keeps a project’s skills, subagents and extensions in chest.toml and pins them in chest.lock. yapi runs each chest extension with only the capabilities its entry grants. Use it for packages that belong in a project’s repository, and yapi install for packages you want in every project, as in Pi. Choose between chest and yapi install compares the two.

Package manifests

yapi reads the pi key of package.json to find a package’s resources. Two more sources can list them, and for each kind of resource the first source that lists it wins:

  1. The [package] table of a chest.toml in the package.
  2. The yapi key of package.json, with the same shape as pi.
  3. The pi key.

This lets one package ship a native build for yapi and JavaScript for Pi, and lets a package without package.json list its resources in chest.toml.

When a pi key exists, or [package] or yapi lists some kind, a kind that no source lists provides nothing, as in Pi. Otherwise the package uses the conventional folders: extensions, skills, prompts and themes. A yapi key that holds only capabilities therefore hides neither the pi lists nor the folders. yapi loads .wasm files from extensions as native extensions.

Pi’s package documentation covers the manifest format.

The built-in npm client

yapi has a built-in npm client. It resolves versions with npm’s range syntax, verifies integrity hashes and lays out node_modules as npm does.

A package over any of these limits fails the install and leaves nothing behind:

  • Registry metadata: 256 MiB to download
  • Tarball: 512 MiB to download, unpacking to at most 2 GiB in at most 200,000 entries

The client doesn’t run lifecycle scripts. Packages that build native addons do it in those scripts, and the WebAssembly runtime can’t load native addons. Such addons install unbuilt and fail only if an extension loads one.

The client reads registries and credentials from npm_config_* environment variables and from ~/.npmrc, or the file npm_config_userconfig names. It reads registry, @scope:registry and each registry’s _authToken, _auth, or username and _password, and expands ${VAR} references. Credentials go only to the registry their key names.

A request that takes longer than fetch-timeout milliseconds, 5 minutes by default, fails the install. 0 sets no limit. This .npmrc sends a token from the environment to a scoped registry:

@acme:registry=https://npm.acme.dev/
//npm.acme.dev/:_authToken=${ACME_NPM_TOKEN}

Pi’s npmCommand setting replaces the built-in client for installing and updating npm sources. Removals and the dependencies of git packages always use the built-in client.

Connect MCP servers

yapi connects to Model Context Protocol (MCP) servers over stdio and streamable HTTP. This page covers describing and managing servers, signing in, servers that extensions register, and codemode, which lets the model call MCP tools from a script.

Describe servers in mcp.json

Describe servers in ~/.yapi/agent/mcp.json, or in .yapi/mcp.json for one project. This file adds a stdio server that npx starts and an HTTP server with a bearer token from the environment:

{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "."]
    },
    "docs": {
      "url": "https://example.com/mcp",
      "headers": { "Authorization": "Bearer ${DOCS_TOKEN}" }
    }
  }
}

Pi’s MCP documentation describes every option.

A project-only run connects the project’s servers. From ~/.yapi/agent/mcp.json, it connects only the servers that mcpServers in your projectOnly setting names.

Manage servers

yapi mcp edits the file and checks servers without starting a session. These commands add the two servers above, list them and remove one:

yapi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
yapi mcp add docs --url https://example.com/mcp \
  --bearer-token-env-var DOCS_TOKEN
yapi mcp list
yapi mcp remove docs

yapi mcp list shows each server’s state, tools and errors, and exits with 1 if a server fails.

Inside yapi, /mcp opens a manager that lists each server with its state, tool count, exposure and configuration file. Select a server to see its tools, reconnect, sign in or out, change its exposure, or enable or disable it. yapi saves exposure and enabled changes to the mcp.json that defines the server. Outside interactive mode, /mcp prints the status, and /mcp login, /mcp logout and /mcp reconnect act on a server directly.

Sign in to a server

HTTP servers without an Authorization header sign in with OAuth. A server that needs a sign-in shows it in /mcp and yapi mcp list. Select it in /mcp, or run /mcp login <server> inside yapi or yapi mcp login <server> in a terminal. logout deletes the stored credentials.

yapi opens the authorization page in your browser and waits for the redirect. It opens only http and https pages and fails the sign-in when a server names another scheme. If the browser runs on another machine, paste the URL it was redirected to.

yapi registers itself with servers that allow it. For other servers, set a pre-registered client in the server’s oauth object, or pass --oauth-client-id and the related options to yapi mcp add. The oauth object takes clientId, clientSecret, callbackPort or callbackUrl, scope, clientName and authServerMetadataUrl.

yapi stores credentials in ~/.yapi/agent/mcp-auth.json, in Pi’s format, and refreshes access tokens before they expire. A running session picks up a sign-in made with yapi mcp login on its next turn.

To send the token of a provider you signed in to with /login instead, add "auth": { "provider": "your_provider_id" } to a server in the global mcp.json.

Servers that extensions register

An extension adds a server for the session with pi.registerMcpServer(name, config), where config takes the same fields as an mcp.json entry, and removes it with pi.unregisterMcpServer(name). A server of the same name in mcp.json takes precedence. Changes to a registered server in /mcp last for the session only.

A stdio server needs the extension’s process grant, and an HTTP server its network grant. Packages from yapi install have both. A chest entry needs all for a stdio server and net for an HTTP one.

As in Pi, registerMcpServer throws for a name that another extension registered, or one whose tool prefix would clash with it, such as my_docs after my-docs. During loading, the error fails the extension’s load, and the extension that loaded first keeps the name.

Call MCP tools through codemode

By default, yapi offers MCP tools through codemode. Instead of one tool call per step, the model writes a short JavaScript program that calls more than one tool and combines their results. Programs run in a fresh WebAssembly sandbox with no file, process or network access of their own. Three settings change what codemode covers:

  • "exposure": "direct" on a server offers its tools to the model directly.
  • --tools read,bash,edit,write,codemode routes the built-in tools through codemode as well.
  • "codemode": { "mode": "only" } in settings.json offers the tools that scripts can call only through codemode.

The first prompt doesn’t wait for servers whose tools only codemode reaches. A script that names a server’s tools, such as tools.mcp__docs__search, waits until that server connects or fails, and a script that searches, lists or describes tools waits for every server still connecting. Aborting the turn ends the wait.

A package that registers its own codemode tool replaces the built-in one, and yapi warns about it at startup.

Scripts can also use the models global to list the catalog and run classifier and image models with the session’s credentials. Pi’s codemode documentation describes the scripting API.

Share skills and subagents

Any agent. chest places skills and subagents in the folders each agent reads. You don’t need yapi. Only the last section is about yapi.

A skill is a folder with a SKILL.md, and a subagent is a .md file. This page covers adding them, choosing the folders chest fills for each agent, how chest places and tracks items, and importing from skills.sh.

List skills and subagents under [skills] and [agents] in chest.toml, or add them with chest add:

chest add git:github.com/anthropics/skills --path skills/pdf
chest add git:github.com/acme/agents --path reviewer.md

chest tells a skill from a subagent by looking at the package. Pass --skill or --agent when it can’t tell.

With --path, an entry installs one item. Without it, the entry installs every skill or subagent the package provides. A local folder that isn’t a skill itself works the same way.

chest installs only skills that are folders with a SKILL.md. It skips or refuses a skill that’s a single .md file, which yapi and Pi also load. A .md file outside a skills folder is a subagent.

Choose folders for your agents

chest init looks for each agent’s folder in the project and offers its skill and subagent folders:

A folder can be a link to another one, such as .claude/skills linking to ../.agents/skills. chest places each item once, in the folder the link resolves to.

How chest copies and links items

The first folder of each kind holds the canonical copy of every item. The other folders get relative links to it, or a copy where chest can’t make a link.

The .gitignore block

chest lists every installed path in a block of the project’s .gitignore, from # BEGIN chest (chest.toml) to # END chest. It rebuilds the block on each install and leaves every other line alone. The block also ignores the .*-staging and .*-old folders that an interrupted install can leave behind, which the next install removes.

Keep hand-written skills in the same folders

Hand-written skills can live in the same folders. chest replaces or removes an item only when it installed the item itself on this machine and the item still holds what chest installed. It also takes over a copy it didn’t record when that copy already holds exactly what the lock pins. chest keeps its record in ~/.chest/state, outside the project.

When someone edits an item after chest installed it, chest leaves the item as it is, even when the lock now pins another version, and installs the other entries as usual. chest install, chest update and chest list show the entry as edited, and chest verify reports the item. To get the locked copy back, delete the item and run chest install. chest install --frozen fails on an edited item instead.

Import from skills.sh

chest import --skills-lock turns the skills of a skills.sh skills-lock.json into skill entries. It reads the skills-lock.json beside the manifest, or the file you name. Run chest install after importing.

Import takes skills from GitHub, GitLab, other git hosts, local folders and node_modules. It skips, with a warning, a skill of another sourceType, a skill the manifest already has, and a different skill whose name the manifest already uses.

What yapi adds

yapi only.

yapi does more with the same entries. When it starts, it puts back missing skills and subagents: those of ~/.chest/chest.toml in every project, and those of the project’s manifest once you trust the project. It also loads skills from folders it doesn’t read on its own. How yapi loads a manifest describes it.

Run yapi extensions

yapi only. chest installs extensions in any project, but only yapi loads them. Other agents ignore [extensions], capabilities and events.

An extension entry installs a Pi package or a native .wasm extension, and yapi loads each one with only the capabilities its entry grants. This page covers granting capabilities, letting extensions share events, how yapi loads a manifest and importing packages from settings.json.

Git and npm extensions go into the extension store, .yapi/chest by default, and a path extension loads where it is. These entries grant one extension everything and another file access:

chest add npm:@acme/pi-subagent --grant all
chest add git:github.com/acme/pi-todo --grant fs

chest add treats a source as an extension when it’s a .wasm, .ts or .js file, or a package that provides extensions or has an index.ts or index.js. Pass --extension when chest can’t tell. chest refuses a source that holds no extension, even with --extension.

Grant capabilities

An extension entry lists what it may reach:

CapabilityAllows
fsReading and writing files, and the read, write, edit and ls tools
netNetwork requests, model calls and provider credentials
envEnvironment variables
sessionStarting turns and changing the session and its files
allEverything above, plus running programs
noneNothing beyond the baseline. The default.

chest add shows the capabilities a package requests and asks about each one. For a native extension, it also asks about the capabilities the build uses that the package doesn’t request, read from the build’s features and the WebAssembly System Interface (WASI) interfaces it imports. A bare .wasm file requests nothing, so chest offers what it uses.

A request never grants anything by itself. Without a terminal, or with --yes, chest grants only what --grant lists, which is nothing by default. --grant applies to extensions only. capabilities-defaults in the manifest adds capabilities to every extension entry of that manifest.

all is the only way to run programs. A program runs as you, outside the sandbox, with yapi’s environment and API keys. So all is full access, and chest add says so before it grants it. What each capability allows gives the exact list.

Let extensions share events

Extensions share pi.events by default, as in Pi, so cooperating Pi extensions keep working whatever their grants. Sharing has a cost between extensions with different grants. One that acts on events lets the sender borrow its access, and one that listens learns what others send.

An entry’s events narrows that. Here todo sends only todo: channels and hears only subagent:done, and scraper neither sends nor hears:

[extensions.todo]
git = "https://github.com/acme/pi-todo"
capabilities = ["fs"]
events = { send = ["todo:*"], receive = ["subagent:done"] }

[extensions.scraper]
npm = "@acme/scraper"
capabilities = ["net"]
events = "isolated"

Extensions with identical grants always hear each other. Across different grants, an event reaches an extension only when the sender may send its channel and the receiver may hear it.

chest add offers the shared default, the channels the package declares, when it declares any, or isolated. Without a terminal, or with --yes, it keeps the shared default. Event bus routing has the rules.

How yapi loads a manifest

At startup and on /reload, yapi reads two manifests:

  • the project’s manifest, when the project is trusted
  • ~/.chest/chest.toml, in every project, except for the entries a project-only run leaves out

A project manifest that installs anything asks for trust, as .yapi files do. A manifest with only a [package] table describes the project as a package and needs no trust. CHEST_MANIFEST can name another project manifest, as How yapi reads CHEST_MANIFEST describes.

yapi puts back every skill, subagent and extension that the lock pins and that’s missing. It also puts back an entry whose copy holds what an older lock pinned, such as after you pull a teammate’s chest update.

With --offline or PI_OFFLINE set, yapi leaves these entries out with a warning instead. So an extension never loads from a copy the lock no longer pins, and neither does a skill in a folder yapi doesn’t read on its own, such as .claude/skills. A skill’s copy in a folder yapi reads on its own, such as .agents/skills, keeps loading, and the warning says so.

yapi leaves out an entry that isn’t locked, or whose lock no longer matches the manifest, and warns you to run chest install, or chest -g install for ~/.chest/chest.toml. A manifest without a lock installs nothing, with the same advice. yapi never writes the lock or the .gitignore block.

An entry under [patch] needs no lock entry. A patched extension loads from its patch. A patched skill loads from where chest install placed it, or else from its patch.

yapi loads the installed extensions as packages named chest:<name>, each with the capabilities and event policy of its entry. Only chest names packages this way, so yapi ignores a packages entry in settings that starts with chest:.

When a native extension uses a capability its entry doesn’t grant, yapi warns at startup, because it will deny those calls. How yapi enforces grants covers the checks.

yapi loads each placed skill from its canonical copy, in the first skills folder. That works even in a folder yapi doesn’t read on its own, such as .claude/skills. A skill in a folder yapi also reads on its own, such as .agents/skills, loads once, as chest’s.

When two skills share a name, the first one yapi loads keeps it, as in Pi. Load order also decides which extension a tool conflict names. yapi loads resources in this order:

  1. The paths that the project’s settings list under skills, extensions, prompts and themes
  2. The project’s chest entries
  3. The project’s folders that yapi reads on its own, such as .yapi/skills and .agents/skills
  4. The paths that your global settings list under those keys
  5. The entries of ~/.chest/chest.toml
  6. The global folders, such as ~/.agents/skills and the agent folder’s skills and extensions
  7. The packages from settings, in Pi’s order

yapi never removes placed copies. After you remove an entry from the manifest, or while its lock is stale, its copies in folders yapi reads on its own, such as .agents/skills, keep loading until chest install removes them.

Before it opens, yapi config puts back missing entries as a run does. It lists chest’s extensions and skills marked as managed by chest, and Space doesn’t toggle them, because the manifest decides what loads. In the Global Resources view, ctrl+o can still keep a global chest item in project-only runs.

When a package is installed both ways

A package can be a chest entry and also a packages entry in settings, such as after chest import --settings or a yapi install of a package the project’s manifest lists. Two copies would register the same tools, and a tool registered twice stops yapi, as in Pi. So yapi loads an npm or git package once, from the first of these that installs it:

  1. The project’s manifest
  2. The project’s settings
  3. ~/.chest/chest.toml
  4. Your global settings

Two entries of one manifest that install the same package count too, and the first one loads. An entry with path counts as the same package as a copy of the whole package, but two entries that take different folders of one repository both load. An entry with a [patch] counts as the package it names, so when it loads, its patch loads in place of the other copies.

yapi leaves out the other copies and warns about each one at startup, with the command that removes it:

  • yapi remove -l <source> for a copy in the project’s settings, with --approve while your trust in the project isn’t saved
  • yapi remove <source> for a copy in your global settings
  • chest remove <name> for an entry of the project’s manifest, or chest --manifest <file> remove <name> for one that CHEST_MANIFEST names
  • chest -g remove <name> for an entry of ~/.chest/chest.toml

Between the project’s settings and yours, Pi’s rule applies, and the project’s entry wins. A path package installed both ways names the same files, so they load once, with the chest entry’s capabilities.

An extension file that two chest entries give, such as one path in both manifests, loads once too, with only the capabilities and event channels that both entries grant. yapi warns at startup with both entries and what it narrowed. To give the file what one entry grants, remove the other entry or grant the same in both.

A file that a loaded entry gives runs with no capabilities when an entry that yapi leaves out holds it too, such as a second entry with the same path that isn’t locked yet. yapi warns at startup with both entries. To give the file its capabilities back, remove the entry that doesn’t load, or run chest install so that both load and the file gets only what both entries grant.

Import packages from settings.json

chest import --settings turns the packages of .yapi/settings.json, or the settings.toml that replaces it, into extension entries with capabilities = ["all"], which is what yapi install gives them. It keeps their skills, prompts and themes filters. chest has no extensions filter and no autoload: false. chest leaves out a package that sets either, with a warning, and the package keeps loading from settings.json.

Each entry is named after the last part of its source. Import skips a package the manifest already has, at any version, and a different package whose name the manifest already uses. To import that one, add it under another name with chest add <source> --name <name>.

Import leaves settings.json alone. For each package it imports, it prints the yapi remove -l command to run once chest installs it. Run the command from the project folder, because -l edits the .yapi/settings.json of the current folder. Until you trust the project, the command includes --approve, because yapi remove -l changes only a trusted project’s settings.

With -g, import reads the agent folder’s settings.json into ~/.chest/chest.toml, which chest -g install installs, and prints yapi remove commands without -l.

After importing, narrow each entry’s capabilities and run chest install right away. Then run the yapi remove commands that import printed. Until chest install locks an entry, yapi leaves it out:

  • An npm or git package loads from the copy in settings, with every capability.
  • A path package’s files belong to the chest entry, which doesn’t load yet, so they run with no capabilities. That’s on purpose: a file that chest manages never runs with more than its entry grants.

Once chest installs an entry, yapi loads chest’s copy and leaves out the one in settings, with a warning, until you remove it.

Lock, verify and update packages

Any agent. The lock pins skills and subagents for every agent, and extensions for yapi.

chest.lock makes installs reproducible: every clone installs exactly what the lock pins. This page covers what the lock records, how installs use it, running chest in CI, verifying installed copies and updating entries.

What the lock records

chest.lock records each entry’s commit or npm version, the tarball and integrity of every npm package in its tree, and a content hash of each installed item. chest writes it, so don’t edit it. The chest.lock reference describes the format and the hash.

A pinned tarball must come from the registry configured for its package, at the standard <name>/-/<file>.tgz path. Tarballs pinned on registry.npmjs.org come from your registry when it’s a mirror. chest refuses registries that keep tarballs elsewhere, such as GitHub Packages. It does so when chest add or chest install resolves the package, before it writes a lock.

Install from the lock

chest install has two modes:

  • chest install: keeps what’s locked and present, installs what’s locked but missing exactly as locked, and resolves entries that changed in the manifest. Then it writes the lock.
  • chest install --frozen: installs exactly what the lock pins, as npm ci does. It puts back what’s missing, and replaces copies that chest installed for an older lock when nobody changed them since. It fails when the lock is missing or out of date, when someone edited a copy, or when a copy doesn’t match its hash because chest didn’t install it. It never writes chest.toml or chest.lock.

Run chest in CI

chest install runs frozen by default when CI holds anything but an empty value, 0 or false. A fresh clone in CI then gets every skill, subagent and extension exactly as locked. The job fails when someone changed the manifest without updating the lock.

Verify installed copies

chest verify checks every installed copy, copy fallback and link against the lock. The lock has no hash for a path entry or for what a [patch] installs, so chest checks those copies against what it installed. It also reports a path entry whose source is gone. verify exits with 1 when an item is missing or doesn’t match.

Update entries

Any agent, except the warning about extension requests, which matters only in yapi.

chest outdated lists entries whose source has a newer commit for its rev, or a newer npm version in range. It also shows npm’s latest when that’s newer than what the range allows. An npm entry already at the newest version in its range is listed only when latest is newer, with no update:

skills.review  1.2.0  (latest 2.0.0 is outside its range)

To move to it, change the entry’s version and run chest install.

chest update moves the named entries, or all of them, to the versions chest outdated lists, installs them and writes the lock. A path extension shows as unchanged even after its files change, since yapi loads it from its source. A copy that someone edited stays as it is while the lock moves on, and its entry shows as edited.

When an updated extension now requests capabilities or event channels beyond its grants, chest update warns and grants nothing more.

One command at a time

One chest command at a time changes a manifest or installs from it. Another one waits for as long as the first runs, and says once that it’s waiting. A frozen install fails instead when another command changes the manifest while it runs. A command that stopped without letting go of its lock holds it for 30s at most.

Environments, global packages and patches

Any agent, except the sections marked yapi only.

One project can keep more than one manifest, and one manifest in your home folder serves every project. This page covers manifests per environment, how yapi chooses a manifest, global packages and installing an entry from a local checkout.

Keep a manifest per environment

Any agent.

A manifest’s lock sits beside it, with .lock in place of .toml. Keep an environment’s entries in a separate, complete manifest, such as chest.dev.toml, which locks in chest.dev.lock. Select it with --manifest:

chest --manifest chest.dev.toml install

CHEST_MANIFEST sets the default for --manifest, as a file name or a path inside the current folder. A value that’s absolute, starts with ~ or uses .. is an error. -g ignores the variable. This sets the same manifest for every command in the shell:

export CHEST_MANIFEST=chest.dev.toml
chest install

The manifests of one project, such as chest.toml and chest.dev.toml, can share folders. A path that one of them drops stays while another still lists it. Each manifest keeps its own block in .gitignore, named after it, such as # BEGIN chest (chest.dev.toml).

How yapi reads CHEST_MANIFEST

yapi only. Other agents read only the folders chest fills, so the variable means nothing to them.

yapi reads the same variable, relative to the project folder, and loads only a manifest inside the project. For a value that’s absolute, starts with ~ or uses .., yapi warns and loads no project manifest. The global manifest still loads.

chest refuses the same values, so chest and yapi always agree on the manifest. Project packages from chest lists the files yapi reads.

Install global packages

Any agent. Only yapi loads global extensions, and it reads the global manifest in every project, unless a project-only run can keep none of its entries.

-g uses ~/.chest/chest.toml instead of the project’s manifest. Its folders can be anywhere under your home folder, such as ~/.claude/skills. Its extensions go to ~/.chest/store, and it writes no .gitignore. Skills and subagents installed this way reach every project, for yapi and for the other agents that read those folders.

With -g, chest init looks for each agent’s folder in your home folder:

Develop a package locally

Any agent.

[patch] installs an entry from a local folder instead of its source, without changing the lock:

[patch]
todo = { path = "../pi-todo" }

A path that points outside the project gets a notice on each install. chest refuses a path source or patch whose folder holds one of its install folders or the store, because chest would copy it into itself.

chest also refuses an extension’s path source or patch whose folder is or holds the home folder, the agent folder, the filesystem’s root or the project, because the extension could load any file there.

chest list shows a patched entry as patched, as edited when someone changed a copy that chest installed from the patch, and as missing when that copy is gone. chest verify reports both. chest install puts a missing copy back from the patch, also with --frozen, which fails on an edited copy instead.

yapi loads a patched entry without a lock entry, as How yapi loads a manifest describes.

Run yapi with only the project’s packages

yapi only.

yapi --project-only loads the project’s extensions, skills and Model Context Protocol (MCP) servers, and leaves out the ones you installed globally. Use it to check that a project’s chest.toml covers what the project needs, or to keep your personal extensions out of a CI run. It works in projects without a chest.toml too.

Only what you installed stays out. Your settings, sign-ins and instruction files such as ~/.yapi/agent/AGENTS.md still apply, so your project-only run can still differ from a teammate’s.

This page covers turning the mode on, what loads, keeping global items such as a theme, and checking what loaded.

Turn on project-only mode

Pass the flag for one run, or set YAPI_PROJECT_ONLY for every run in a shell:

yapi --project-only
export YAPI_PROJECT_ONLY=1

YAPI_PROJECT_ONLY accepts 1, true or yes, and unset YAPI_PROJECT_ONLY turns it off. /reload keeps the mode on.

Programs that yapi starts inherit the variable: bash commands, extension processes, stdio MCP servers and subagents that start another yapi.

Only yapi runs follow the mode. yapi install without -l still adds a package to your global settings, and a project-only run then leaves it out. To add a package to the project, use chest add or yapi install -l.

What a project-only run loads

From a trusted project, yapi loads:

  • the project’s chest entries
  • the packages and resource paths in .yapi/settings.json
  • .yapi/extensions, .yapi/skills, .yapi/prompts and .yapi/themes
  • the servers in .yapi/mcp.json
  • .agents/skills in the project and each parent folder up to the repository root, or up to / outside a repository

In every project, it also loads the built-in extensions, following your +builtin: and -builtin: choices. So do the paths you pass with -e, --skill, --prompt-template and --theme.

It leaves out the rest of what you installed globally, unless you keep some of it:

  • the packages and resource paths in ~/.yapi/agent/settings.json
  • ~/.yapi/agent/extensions, ~/.yapi/agent/skills, ~/.yapi/agent/prompts and ~/.yapi/agent/themes
  • ~/.agents/skills
  • the entries of ~/.chest/chest.toml
  • the servers in ~/.yapi/agent/mcp.json

Your settings, sign-ins, models, key bindings and trust decisions don’t change. AGENTS.md and CLAUDE.md still load from the project, its parent folders and ~/.yapi/agent, and --no-context-files turns them off. SYSTEM.md and APPEND_SYSTEM.md load from the project, or else from ~/.yapi/agent.

A trusted project can still load one of your global files on purpose. It can name the file’s path in its own settings, or add an autoload: false entry for a package you installed. You approved those files when you trusted the project.

Keep some global items

To keep a global theme, skill or MCP server in project-only runs, list it under projectOnly in your global settings:

{
  "projectOnly": {
    "packages": ["npm:@acme/pi-themes", "chest:notes"],
    "extensions": ["extensions/notify.ts"],
    "skills": ["~/.agents/skills/pdf"],
    "themes": ["*"],
    "mcpServers": ["github", "linear*"]
  }
}

yapi reads projectOnly only from ~/.yapi/agent, never from a project’s settings, so a repository you clone can’t turn your global extensions back on. Every key is optional, and prompts works like extensions.

Keep whole packages

packages keeps every extension, skill, prompt template and theme a global package provides. Write each source the way your global packages list writes it, such as npm:@acme/pi-themes or git:github.com/acme/tools. Versions don’t count, so npm:@acme/pi-themes also keeps a package installed as npm:@acme/pi-themes@^2.

Write chest:<name> for an entry of ~/.chest/chest.toml, and * to keep every global package and chest entry. * doesn’t cover loose files in your global folders, such as ~/.yapi/agent/extensions, which the lists below do.

Keep single extensions, skills, prompts or themes

extensions, skills, prompts and themes each keep the resources of their kind that a pattern matches. They work wherever the resource comes from: a global folder, a path in your settings, a global package or a chest entry. Patterns use Pi’s glob syntax, and each one is matched against:

  • the path inside ~/.yapi/agent, such as extensions/notify.ts or themes/dark.json
  • the file name, such as notify.ts
  • the whole path, with ~ for your home folder, such as ~/.agents/skills/pdf

A skill’s folder matches too, so ~/.agents/skills/pdf keeps ~/.agents/skills/pdf/SKILL.md. "themes": ["*"] keeps every global theme, including the ones inside packages, without loading those packages’ extensions.

Your theme setting doesn’t keep a theme by itself. If it names a global theme that themes doesn’t keep, yapi uses the system theme. Interactive mode shows Pi’s error, Failed to load theme "<name>": Theme not found: <name>.

Keep MCP servers

mcpServers keeps servers from ~/.yapi/agent/mcp.json by name, and accepts patterns such as linear*. A kept server keeps its auth, so a server that sends a token from /login still works. The project’s own servers in .yapi/mcp.json always connect.

Global packages yapi still installs

A project-only run installs or restores a global package only when projectOnly could keep part of it:

  • a package that packages names
  • every global package, when packages holds * or another list has an entry, because a pattern can match a file inside any package
  • the missing entries of ~/.chest/chest.toml, in either of those cases or when packages names a chest: entry

With no projectOnly list, a project-only run downloads nothing for your global packages.

Keep items from yapi config

You can also build the list in yapi config, which opens on the Global Resources view. Select an extension, skill, prompt template or theme and press ctrl+o to keep it. Kept items show project-only, and ctrl+o again stops keeping the item.

ctrl+o works on chest items too, which Space leaves alone. It does nothing in the project view that Tab opens, because yapi ignores a project’s projectOnly. yapi config doesn’t list packages or MCP servers, so edit packages and mcpServers in the settings file.

Check what loaded

The header at startup lists the loaded skills, prompt templates and extensions with their scope, and /mcp lists the MCP servers. If the quietStartup setting hides the header, start yapi with --verbose.

Untrusted projects

yapi never loads an untrusted project’s files, in project-only runs or otherwise. When an untrusted project has files that need trust, print, JSON and RPC modes warn once:

--project-only: the project isn't trusted, so none of its packages load

Interactive mode asks whether to trust the project before it starts instead. If you choose not to trust it, yapi shows Pi’s notice that the project’s resources and packages are ignored.

Either way, the run then has only the built-in extensions, the paths you passed on the command line and the global items you keep. Trust the project, or pass --approve for one run. Project trust covers the details.

Publish a package

Any agent, except the sections marked yapi only.

A package that others add with chest describes itself in its own chest.toml. This page covers the [package] table, requesting capabilities and events, and checking a native extension before you publish it.

Describe the package

Any agent, except capabilities, events, and the extensions, prompts and themes lists, which only yapi uses.

A package describes itself in the [package] table of its own chest.toml. chest init --package adds one. It names the package after its folder, at version 0.1.0, requests no capabilities, and lists the conventional folders it finds. A finished table looks like this:

[package]
name = "acme-review"
version = "1.3.0"
description = "Code review skills and a reviewer subagent"
capabilities = ["fs", "session"]

chest add and chest list show the name, version and description. skills and agents list what the package provides to any agent. Publish the package to npm or push it to a git repository, and others add it with chest add.

The [package] reference lists every key, and Package metadata explains how chest falls back to package.json.

chest doesn’t install the entries in the package’s own [skills], [agents] or [extensions] sections for its consumers. chest add lists them so the consumer can add the ones they want.

Request capabilities and events

yapi only.

capabilities and events are requests. chest add shows them to the consumer, who decides what to grant. A package can also request them in package.json under yapi.capabilities and yapi.events.

Check a native extension

yapi only.

Before you publish a native extension, run chest check in the package folder. It compares the capabilities each .wasm extension uses with the ones the package requests:

chest check

It reads the capability features the extension was built with, and the WebAssembly System Interface (WASI) interfaces it imports. An import of wasi:filesystem, for example, counts as using fs.

chest check reports an error and exits with 1 when it finds either of these:

  • a capability the extension uses that the package doesn’t request
  • an import of wasi:sockets or wasi:http, which yapi doesn’t support, because extensions reach the network through the SDK’s fetch

It warns about these and still exits with 0:

  • a capability the package requests that no extension uses
  • a capability the build records that this version of chest doesn’t know, such as one a newer SDK adds, which chest doesn’t check

chest add also warns when an extension imports wasi:sockets or wasi:http.

An extension built without yapi-extension-api has no record of its features, so chest checks only its imports. JavaScript and TypeScript extensions have nothing to read before they run, so yapi checks them only at runtime.

Entry states

chest list shows each entry in one of these states:

  • installed: in place as the lock pins it
  • edited: a copy changed since chest installed it, whatever the lock pins now
  • outdated: in place as an older lock pinned it
  • stale: not locked, or the lock no longer matches the manifest
  • patched: under [patch]
  • missing: locked but not in place
  • no source: a path entry whose source is gone. chest install skips it with a warning and installs the other entries, and chest install --frozen fails on it. Restore the folder or remove the entry.

yapi acts on the same states at startup. It doesn’t hash copies, so it treats an edited entry as installed, or as outdated when the lock pins another version.

Use a proxy

chest reads proxy variables such as HTTPS_PROXY, as yapi does. Without them, it uses the httpProxy setting in yapi’s global settings.json, like yapi.

Exit codes and prompts

chest exits with 0 on success, 1 when a command fails or verify or check finds a mismatch, and 2 on a usage error. Questions go to stderr, and chest asks them only at a terminal.

chest.toml reference

Any agent, except the keys and sections marked yapi only.

Which manifest chest uses

Any agent. yapi reads CHEST_MANIFEST too, as How yapi reads CHEST_MANIFEST describes.

chest picks one manifest per command:

  • chest uses chest.toml in the current folder, and only there.
  • --manifest <path> names another, and CHEST_MANIFEST sets the default for it.
  • An environment’s manifest is a complete manifest of its own, such as chest.dev.toml. Its lock is the same name with .lock for .toml, here chest.dev.lock.
  • -g uses the global manifest, ~/.chest/chest.toml. It can’t be combined with --manifest.
  • chest refuses a chest.toml or chest.lock that’s a symbolic link, so a cloned project can’t point chest at a file outside it.

Paths in a manifest are relative to the manifest’s folder. A project manifest keeps every folder inside the project. The global manifest may use ~ and absolute paths, and installs only inside your home folder.

What each capability allows

chest.lock

Any agent.

chest writes the lock, so don’t edit it. It holds version = 1 and one table per entry, in [[skill]], [[agent]] and [[extension]], sorted by name:

FieldMeaning
nameThe entry
git, rev, commitThe repository, the revision asked for, and the 40-character commit it resolved to
npm, versionThe package and the version installed
pathThe subpath, or the source of a path entry
tarball, integrityFor an npm skill or subagent, its tarball and sha512 integrity

Path entries record their path only, with no hash, and [patch] entries never appear. What the lock records covers where a pinned tarball may come from.

The lock is up to date when every entry has a record with:

  • the same section and name
  • the same source kind, location and subpath
  • the same rev
  • a locked npm version that still satisfies the entry’s range

Capabilities, events and filters never make it stale.

How chest computes the content hash

The hash is sha256- followed by lowercase hex:

  1. List every regular file under the item’s folder, skipping anything named .git at any depth, a folder or the file a worktree or submodule has. A symbolic link anywhere else fails the hash. An item that’s one file is a list of that file with an empty path.
  2. Sort the files by the bytes of their paths, relative to the item, with / between parts.
  3. For each file, feed one SHA-256 with its path in UTF-8, a zero byte, x when any execute bit is set or - otherwise, and the 32-byte SHA-256 of its contents.
  4. The result is that SHA-256, in hex.

Extend yapi with extensions

Extensions add tools, commands, flags, event handlers and interface components. This page compares the two extension types, then covers loading extensions, writing a Pi extension, compatibility with Pi, yapi’s own APIs, how Pi extensions run, crashes and providers. yapi runs both types on one WebAssembly host:

  • Pi extensions: written in TypeScript or JavaScript, they run unchanged.
  • Native extensions: written in Rust and compiled to WebAssembly components.

Both types load from the same places, ship in the same packages and use the same events and interface model.

Choose an extension type

The two types differ in runtime, isolation and portability:

Pi extensionNative extension
LanguageTypeScript or JavaScriptRust
Runs inPi and yapiyapi only
RuntimeQuickJS-NG, a JavaScript interpreter without a just-in-time (JIT) compiler, compiled to WebAssemblyMachine code that Wasmtime compiles from the extension’s WebAssembly
InstanceOne instance shared by the Pi extensions with the same grants and event policyAn instance of its own
MemoryShared by the Pi extensions in its instanceIts own
ComputeWhile one Pi extension computes, the others in its instance waitDoesn’t block other extensions
After a crashIts instance restarts and the Pi extensions in it reloadOnly this extension restarts
APIPi’s ExtensionAPI from Pi 1.0, with the exceptions in Differences from Piyapi’s Rust SDK, unstable until yapi 1.0
Dependenciesnpm packages in plain JavaScriptRust crates that build for wasm32-wasip2

Both types run under the same compute and memory limits.

Pi extensions are the better choice when:

  • the extension should also run in Pi, or already exists as a Pi package
  • it needs parts of Pi’s API that the native SDK doesn’t cover yet: providers, Model Context Protocol (MCP) servers, model classification and image generation, and session actions such as ctx.newSession and ctx.fork
  • it builds on npm libraries, or benefits from editing without a build step

Native extensions are the better choice when:

  • the extension does heavy computation, which compiled code runs faster than an interpreter
  • it should be isolated from other extensions, since a native extension’s crash doesn’t reload the others
  • memory matters. Native extensions don’t load the JavaScript runtime, and the benchmark measures the memory that Pi extensions add.
  • the code base is in Rust, or should use Rust crates

Weigh these limits as well:

  • A Pi extension that needs Node features the runtime lacks, such as native addons, net and tls servers or worker_threads, can’t run in yapi. Differences from Pi lists them.
  • A native extension needs the Rust toolchain to build, and you may need to rebuild it for a new yapi release until 1.0.

One package can ship both types. A yapi key in package.json names the native build for yapi, and the pi key names the JavaScript build for Pi. See Package manifests.

Where yapi loads extensions from

yapi loads extensions from three places:

  • ~/.yapi/agent/extensions, and .yapi/extensions in a trusted project
  • packages and files added with yapi install, which accepts npm and git sources, local folders and single .ts, .js or .wasm files
  • -e <source> for one run, which accepts a file, a package folder, or an npm or git source

yapi -ne starts without extensions, and yapi config turns single extensions off. A chest manifest adds a project’s extensions too, each with the capabilities its entry grants.

/reload loads every extension again from disk, so edits and rebuilt native extensions take effect. A new, resumed, forked or cloned session picks up added and removed extension files and installs packages added to settings, but keeps the extensions it already loaded until /reload. A session in another working folder loads every extension again.

Request capabilities

A package can say which capabilities it needs, from fs, net, env, session and all, and which pi.events channels it sends and hears. List them as capabilities and events in the [package] table of a chest.toml in the package, or in the yapi key of package.json:

{
  "yapi": {
    "capabilities": ["fs"],
    "events": { "send": ["todo:*"], "receive": [] }
  }
}

A request grants nothing. chest shows it when a project adds the package, and the project’s manifest decides what the package gets. A package from yapi install gets every grant whatever it requests.

Test a package under the grants it requests, so yapi doesn’t refuse a call it needs once others install it. What each capability allows lists what each capability covers.

Write a Pi extension

Code renderers

yapi shows code in one color. pi.yapi.registerCodeRenderer(render) lets an extension color it, or draw it differently, in Markdown code blocks, read and write tool rows and codemode scripts. This renderer colors three SQL keywords:

pi.yapi?.registerCodeRenderer((code, lang, { width }, theme) => {
  if (lang !== "sql") return undefined;
  const keyword = /\b(SELECT|FROM|WHERE)\b/g;
  return code
    .split("\n")
    .map((line) =>
      line.replace(keyword, (word) => theme.fg("syntaxKeyword", word)),
    );
});

A renderer follows these rules:

  • lang is the code block’s language or the file’s language, and may be undefined.
  • Return the styled lines, or undefined to keep the plain code.
  • When more than one extension registers a renderer, yapi uses the first one that returns lines.
  • Code shows plain until the renderer returns.

How Pi extensions run

Pi extensions run in yapi-js, a QuickJS-NG runtime compiled to WebAssembly, so yapi needs no Node.js. These details shape how they run:

  • @earendil-works/pi-coding-agent, pi-ai, pi-agent-core, pi-tui and typebox resolve to copies bundled with yapi. pi-ai is Pi’s own code, with its wire APIs and image generation on yapi’s providers.
  • pi-agent-core, pi-tui and the parts of pi-coding-agent that run inside an extension, such as session entry helpers, compaction, skills and the interface components, are Pi’s own code, loaded the first time an extension uses them. They use yapi’s folders.
  • Exports that would reach provider credentials, project trust, settings or session files without the host throw, as Differences from Pi lists.
  • Built-in tool factories return yapi’s tools, which yapi runs, or Pi’s own over custom operations, as Pi’s ssh example uses them.
  • yapi resolves modules as Node does and strips TypeScript types, with a cache keyed by file content.
  • Shims provide Node’s fs, path, os, child_process, events, stream, util, crypto hashes, buffer, timers, fetch, dns.lookup and Intl. Native addons, net and tls servers and worker_threads fail when used, and the rest of the extension keeps working.
  • Dates use the local time zone, from TZ or the system, as in Node.
  • Interface components render inside the runtime. yapi paints their last frame, so a slow extension never blocks the interface.
  • pi.events reaches extensions in other runtimes according to their grants and event policies. By default an extension sends and hears every channel, as in Pi, and a chest entry can narrow that, as Event bus routing describes.

Differences from Pi lists where the behavior differs.

What happens when an extension crashes

A crashed instance restarts and its extensions reload. yapi reports the crash as an extension error, closes the instance’s dialogs and widgets, and restores the built-in editor, footer and header. Tool calls and messages it drew stay in the transcript, and the restarted instance draws them again. How the extension sandbox works describes the limits of each instance and what extensions may access.

Providers from extensions

pi.registerProvider() adds a provider and its models. They appear in /model and work with --model and the set_model command of remote procedure call (RPC) mode. An extension can register a provider at any time, such as from a command or an event handler, and the change applies at once.

A configuration registered again for the same provider keeps the previous configuration’s values for the keys it leaves undefined. pi.unregisterProvider() removes a provider whichever extension registered it, and restores the built-in or models.json provider it replaced. What a provider does depends on what it defines:

  • A provider configured like a models.json entry streams through yapi’s implementation of its api.
  • A provider with its own streamSimple can implement an API yapi doesn’t have, or pass requests to pi-ai’s built-in APIs, such as anthropicMessagesApi(). A stream registered with pi-ai’s registerApiProvider serves every model of its API, including ones from models.json. Provider hooks such as before_provider_request run either way.
  • A provider with oauth adds its sign-in to /login. yapi stores its credentials in auth.json and refreshes them before they expire.
  • A provider with refreshModels updates its model list whenever yapi refreshes model catalogs.
  • A provider with the legacy oauth.modifyModels adjusts its models for the signed-in account whenever yapi refreshes model catalogs.
  • Image and classifier models run through the provider’s images and classifiers implementations for their api. Codemode scripts and extensions use them with generateImages and classify.
  • A complete pi-ai Provider, such as one createProvider builds, brings its own models, API key and OAuth sign-in, streams, image and classifier implementations and model refresh. /login asks for its API key with the provider’s own login, or says the key is set up outside yapi when it has none.
  • A pi-ai Provider’s API key check, filterModels and filterAllModels decide which of its models are available for the stored credential, or for the key --api-key gives. They run as the extension loads, whenever yapi refreshes model catalogs, after you sign in or out, and after an extension registers or unregisters a provider. See Differences from Pi.

Pi’s custom provider documentation describes the configuration.

Write native extensions in Rust

Native extensions are WebAssembly components written in Rust with the yapi-extension-api crate. Like Pi extensions, they register tools, commands, flags, event handlers and interface components, and they use Pi’s JSON shapes for events and results. Each one runs in a WebAssembly instance of its own, with no JavaScript runtime. This page covers creating, building, testing and sharing an extension, then the SDK’s API.

The native extension API is unstable until yapi 1.0. The Wasm Interface Type (WIT) world, the Rust SDK and the host requests may change in any release before then, and you may need to rebuild extensions. Pi extensions aren’t affected.

Create an extension

The SDK needs Rust 1.88 or newer, or 1.91 with the widgets feature. Add the wasm32-wasip2 target to your Rust toolchain:

rustup target add wasm32-wasip2

Create a project:

yapi new shout

yapi new writes a Cargo project that’s also a yapi package:

The package takes the folder’s name, or the one --name gives. Names use lowercase ASCII letters, digits, - and _, and start with a letter. The same template works with cargo-generate:

cargo generate --git https://github.com/SkymanOne/yapi --tag v0.4.2 \
  crates/yapi/templates/extension

To start without the template, create a library crate with crate-type = ["cdylib"] and depend on the SDK version of the yapi release you target:

[dependencies]
yapi-extension-api = "0.4.2"

An extension registers its features in an init function and exports it with extension!. Tools, commands and event handlers are async closures. This src/lib.rs registers a shout tool and a /hello command:

#![allow(unused)]
fn main() {
use yapi_extension_api::{Api, Tool, ToolResult, json, notify};

fn init(api: &mut Api) {
    api.register_tool(Tool::new(
        "shout",
        "Repeats the text in capitals",
        json!({
            "type": "object",
            "properties": {"text": {"type": "string"}},
            "required": ["text"]
        }),
        |params, _ctx| async move {
            let text = params["text"].as_str().unwrap_or_default();
            Ok(ToolResult::text(text.to_uppercase()))
        },
    ));
    api.register_command("hello", "Says hello", |args, _ctx| async move {
        let name = if args.is_empty() { "world" } else { &args };
        notify(&format!("Hello, {name}!"), "info");
        Ok(())
    });
}

yapi_extension_api::extension!(init);
}

Build the extension, then copy shout.wasm from Cargo’s target folder into the package’s extensions folder:

cargo build --release
cp target/wasm32-wasip2/release/shout.wasm extensions/

A crate without the template’s .cargo/config.toml builds with cargo build --release --target wasm32-wasip2.

Declare capabilities

The features of yapi-extension-api declare the capabilities an extension uses, the same ones a package requests in capabilities. Each feature enables the requests that need its grant:

FeatureEnables

netfetch, fetch.stream, dns.lookup, and the model and credential operations such as ai.stream and models.apiKey
envenv, which reads environment variables
sessionsend_message, append_entry, and the requests that change the session, such as session.sendMessage, session.reload and model.set

The template starts with session, which its hello code needs:

[dependencies]

A request whose feature the build leaves out fails without reaching yapi, with a message such as request `session.appendEntry` needs the `session` feature of yapi-extension-api. exec, Process, send_message and append_entry exist only with their features. Requests that need a grant only for some payloads, such as tool.execute and ui.editorSubmit, need no feature, and yapi checks them as they run.

Check the build’s capabilities

The build records its features in a yapi:capabilities custom section. After each build, run chest check. It compares the features, and the WebAssembly System Interface (WASI) interfaces the component imports, with the capabilities in the package’s chest.toml or package.json:

cargo build --release
cp target/wasm32-wasip2/release/shout.wasm extensions/
chest check

Check a native extension lists what chest check reports, and chest add shows the same comparison to the person who adds the package. yapi doesn’t provide wasi:http, so a component that imports it doesn’t load, and yapi refuses every wasi:sockets call. Reach the network through the SDK’s fetch with the net feature.

Features declare what an extension uses. They grant nothing: yapi grants capabilities from the manifest that installs the package, and refuses requests beyond them. At startup, yapi warns about a native extension from a chest manifest that uses a capability its entry doesn’t grant, because it will deny those calls.

Move to capability features

Earlier versions of the SDK have no capability features and send every request. An extension that moves to this version stops building where it calls exec, Process, send_message or append_entry, and its other requests that need a grant fail at runtime. To move it:

  1. Enable the features of the requests it sends, from the table in Declare capabilities.
  2. List the same capabilities in capabilities under [package] in chest.toml, or yapi.capabilities in package.json.
  3. Build it and run chest check.

yapi -e .

python3 check-extension.py .

yapi install takes the package folder or the .wasm file, for every project or with -l for the current one:

Host requests

request(kind, payload) sends a request to yapi and returns its JSON answer. yapi supports these kinds for native extensions:

exec.sync runs command with args and waits for it:

  • Without cwd the process starts in yapi’s working folder. env replaces the whole environment, as in Node, and envAdd sets variables on top of the inherited environment or of env.
  • yapi writes input to standard input. timeout kills the process after that number of milliseconds.
  • code is null when a signal ended the process, and killed is true when the timeout did.
  • A process that can’t start answers {"stdout": "", "stderr": "", "code": null, "error"}, where error is Node’s spawn error, such as spawn git ENOENT. The request fails when the extension may not run processes.

Entries have the shapes of Pi’s session files.

ui.notify and the session requests fail while the init function runs, before yapi binds the extension to a session. Every other kind is internal to yapi and may change or disappear in any release.

Background processes

Process::spawn starts a process that runs while the extension does other work. It takes {"command", "args", "cwd", "env", "envAdd", "stdin"}, all optional except command:

  • cwd, env and envAdd work as in exec.sync. "stdin": "ignore" gives the process empty standard input instead of a pipe.
  • Process::next waits for the next ProcessEvent: output on standard output or standard error, then the exit. A dropped next future loses no output.
  • write waits while the process hasn’t taken the previous write. close_stdin and kill act at once.

Dropping a Process kills it, and so does stopping the extension. Process needs the all feature, and starting one needs the process grant, which a chest entry gets only with all.

A process inherits yapi’s environment, so envAdd is how an extension gives it a variable without the environment grant. yapi adds the variables itself, and the extension never sees the values the process inherits. This runs a build script with one added variable:

#![allow(unused)]
fn main() {
let output = request("exec.sync", &json!({
    "command": "sh",
    "args": ["scripts/build.sh"],
    "envAdd": {"BUILD_MODE": "release"},
}))?;
}

Where the extension is

extension_path() returns the extension’s .wasm file as file, and the root of the package it was installed from as package_root. package_root is None for a file given with -e or found in an extensions folder. An extension that starts another yapi with itself loaded passes file to -e, and one that ships scripts or data finds them next to file or under package_root.

Where the project is

project_dir() returns the folder the session’s project files come from, the same folder as projectDir in Context::data. It’s the working folder unless yapi runs with --project-dir. The init function can call it before any Context exists, such as to list project files in a tool’s description.

yapi runs the init function again for every new, resumed, forked or reloaded session, and each run sees the project of the session it loads for. Older versions of yapi answer None, and an extension then falls back to the working folder from the cwd request.

Events between extensions

events::emit(channel, &data) and events::on(channel, handler) are Pi’s pi.events, a bus that every extension shares, native or Pi, whichever runtime it runs in. This extension notifies on deploy:done and emits it from a /deploy command:

#![allow(unused)]
fn main() {
use yapi_extension_api::events;

fn init(api: &mut Api) {
    events::on("deploy:done", |data| {
        let version = data["version"].as_str().unwrap_or_default();
        notify(&format!("Deployed {version}"), "info");
    });
    api.register_command("deploy", "Deploys", |_args, _ctx| async move {
        events::emit("deploy:done", &json!({"version": "1.2.0"}));
        Ok(())
    });
}
}

emit runs the extension’s own handlers for the channel before it returns, in the order they subscribed, as Pi does. Other extensions receive a JSON copy of the data after emit returns, in the order the extension emitted it.

on returns a Subscription, and Subscription::unsubscribe stops the handler. Dropping the Subscription keeps the handler. A handler runs to completion before the next one starts, so a handler that waits for host work starts it with spawn. When the extension loads again for another session, yapi drops every handler and the init function subscribes again.

A busy runtime holds at most 64 events from other runtimes. yapi drops later ones until it catches up and logs a warning, so a stuck extension never holds up the others or the interface.

Events cross between extensions according to their grants and event policies, as Agent sessions and events describes. on tells yapi which channels have handlers, so that yapi can warn when its routing keeps an event from one.

Interface components

A component implements the Component trait. render returns the lines to show at a width, as text with ANSI escape sequences. The optional handle_input receives raw terminal input while the component has focus, and handle_mouse receives mouse events in fullscreen mode and returns whether it took them. This component asks a yes or no question:

#![allow(unused)]
fn main() {
use yapi_extension_api::{Component, CustomOptions, Done, parse_key, theme};

struct Confirm {
    done: Done<bool>,
}

impl Component for Confirm {
    fn render(&mut self, _width: usize) -> Vec<String> {
        vec![theme().fg("accent", "Deploy now? (y/n)")]
    }

    fn handle_input(&mut self, data: &str) {
        if data == "y" || data == "n" {
            self.done.finish(data == "y");
        } else if parse_key(data).as_deref() == Some("escape") {
            self.done.finish(false);
        }
    }
}
}

A command shows it with custom and waits for the answer:

#![allow(unused)]
fn main() {
api.register_command("deploy", "Deploys after asking", |_args, ctx| async move {
    let confirmed = ctx
        .custom(|done| Confirm { done }, CustomOptions::default())
        .await;
    if confirmed == Some(true) {
        // ...
    }
    Ok(())
});
}

It’s false while a selector, a dialog or a component shown with custom has it. A terminal input listener that takes keys from an empty prompt checks it first, so dialogs still get those keys. It returns true without a terminal.

parse_key names common keys, such as up, enter, escape and ctrl+c. It reads both legacy and Kitty keyboard protocol encodings, which differ for Escape and Ctrl keys, so compare keys through it rather than with raw bytes such as "\x1b".

Only the interactive mode shows components. In RPC, print and JSON modes, custom resolves to None at once, and yapi leaves out component widgets, footers and headers. When the extension loads again for another session, yapi drops every component it showed.

CustomOptions::on_handle receives the shown component’s OverlayHandle, Pi’s onHandle. hide closes the component without finishing it, so prefer Done::finish. set_hidden, focus and unfocus only change what is_hidden and is_focused report, as for Pi extensions in yapi, and the overlay stays on screen. An overlay without overlay_options takes the width its component’s Component::width returns, as Pi does with a component’s width.

Replace the editor

Context::set_editor_component puts an EditorComponent in place of the built-in editor, as Pi’s setEditorComponent does, or restores the built-in one with None. The editor starts with the built-in editor’s text. yapi calls its set_text, add_to_history, insert_text_at_cursor and configure methods, and the editor reports back with these:

  • editor_changed when its text changes
  • editor_submit when the user submits
  • editor_action for app keys such as app.interrupt
  • editor_shortcut for extension shortcuts

widgets::CustomEditor is Pi’s CustomEditor: the built-in editor’s keys, history, completions and app keys. Wrap it to change how it handles keys or renders, as Pi’s examples extend it. The modal-editor example adds vim-like modes this way.

Tool and message renderers

Renderers draw tool calls, custom messages and custom entries in the transcript:

  • Tool::render_call and Tool::render_result draw a tool’s call and result, as Pi’s renderCall and renderResult do. Tool::render_shell("self") says they draw the tool’s whole box.
  • Api::register_message_renderer and Api::register_entry_renderer draw custom messages and entries of one type, as Pi’s registerMessageRenderer and registerEntryRenderer do.
  • A renderer returns a component, or None to keep yapi’s own rendering. An entry without a component shows nothing.

The entry-renderer example draws status cards.

Api::register_markdown_transformer is Pi’s registerMarkdownTransformer. It gets a message’s Markdown and Pi’s context, and returns new Markdown or None. A message shows as written until the transformer returns.

A tool renderer gets a RenderContext, with Pi’s context fields such as toolCallId, expanded and isPartial in data, and a state value that the call’s and the result’s renderers share for one tool call. Pi’s lastComponent has no counterpart, so a renderer builds a new component each time yapi asks. The new component takes the old one’s place, and yapi shows the old one’s lines until the new one has rendered.

Code renderers

Api::register_code_renderer is the Rust form of pi.yapi.registerCodeRenderer. It gets the code, its language and the width, and returns styled lines or None. The code-renderer example colors Rust keywords.

Terminal input and completion

Terminal input listeners and autocomplete providers need the all feature. What they return reaches yapi’s own input, where ! runs a shell command and / a slash command.

Context::on_terminal_input adds a listener for raw terminal input, as Pi’s ctx.ui.onTerminalInput does:

  • A listener sees each key before the editor, in the order listeners were added.
  • It returns TerminalInput::Pass to let the key through, Consume to stop it, or Replace(data) to pass on data instead, as Pi’s undefined, {consume: true} and {data}.
  • It stops when you drop the returned Subscription or call unsubscribe, so keep the Subscription as long as the listener should run.
  • editor_text() returns the editor’s text, as Pi’s ctx.ui.getEditorText does, so a listener can take keys only while the editor is empty.

This listener takes the Down key while the editor is empty:

#![allow(unused)]
fn main() {
use std::cell::RefCell;
use yapi_extension_api::{Subscription, TerminalInput, editor_text, parse_key};

thread_local! {
    static LISTENER: RefCell<Option<Subscription>> =
        const { RefCell::new(None) };
}

api.on("session_start", |_event, ctx| async move {
    let listener = ctx.on_terminal_input(|data| {
        if parse_key(data).as_deref() == Some("down")
            && editor_text().is_empty()
        {
            // ...
            return TerminalInput::Consume;
        }
        TerminalInput::Pass
    });
    LISTENER.set(Some(listener));
    Ok(None)
});
}

Context::add_autocomplete_provider adds an AutocompleteProvider over the editor’s completion, as Pi’s ctx.ui.addAutocompleteProvider does:

  • suggestions answers the Suggestions for an EditorState, with Pi’s AutocompleteItem shapes as items. apply answers the editor after the user chooses an item and defaults to Current::apply.
  • Each gets a Current, Pi’s current, which answers for the providers added before, over the built-in completion of commands and paths.
  • trigger_characters names characters that open completion, as @ does.
  • The cursor’s column in EditorState counts bytes, so it slices the line directly.

This provider offers a ticket after # and leaves other text to the providers before it. ctx.add_autocomplete_provider(Tickets) adds it:

#![allow(unused)]
fn main() {
use yapi_extension_api::{
    AutocompleteProvider, Current, EditorState, Suggestions, json,
};

struct Tickets;

impl AutocompleteProvider for Tickets {
    async fn suggestions(
        &self,
        state: &EditorState,
        force: bool,
        current: &Current,
    ) -> Option<Suggestions> {
        let line = &state.lines[state.cursor_line];
        if !line[..state.cursor_col].ends_with('#') {
            return current.suggestions(state, force).await;
        }
        let item = json!({
            "value": "#42",
            "label": "#42",
            "description": "Fix the build",
        });
        Some(Suggestions { items: vec![item], prefix: "#".into() })
    }
}
}

As for Pi extensions in yapi, listeners run while yapi keeps drawing, so keys that arrive together pass through them together. yapi asks providers for suggestions in the background and applies each suggestion as it asks.

Each native extension runs in an instance of its own, and the listeners of every instance see input. Completion goes through the providers of one instance, the one that added a provider last. Only the interactive mode runs listeners and providers.

Background work and cancellation

Handlers are async. While one waits for a host operation, other handlers, tool calls and background tasks run. spawn runs a future in the background after the handler that started it returns, like a promise a Pi extension doesn’t await. A background task can report its result with the session.sendMessage request, with "triggerTurn": true to start a turn when the agent is idle.

When the user aborts a run, yapi drops the futures of the extension tools still running in it, which kills the processes they hold. Background tasks keep running until they finish or the extension stops.

A tool that calls Context::aborted gets the abort instead, as a Pi tool’s signal does. The future resolves when the user aborts the run. The tool keeps running to stop its work, and the result it returns becomes the tool’s result, such as the output so far.

yapi drops a tool that hasn’t returned 10s after the abort. That leaves time to stop a child process with SIGTERM, wait for it and report. Race the future against the work with futures::select! or a small helper, such as race in the countdown example:

#![allow(unused)]
fn main() {
let mut process =
    Process::spawn(&json!({"command": "make", "args": ["test"]}))?;
let mut output = Vec::new();
loop {
    match race(process.next(), ctx.aborted()).await {
        Ok(Some(ProcessEvent::Stdout(bytes))) => output.extend(bytes),
        Ok(Some(_)) => {}
        Ok(None) => break,
        Err(()) => {
            process.kill("SIGTERM");
            while process.next().await.is_some() {}
            output.extend(b"\n[stopped]");
            break;
        }
    }
}
Ok(ToolResult::text(String::from_utf8_lossy(&output)))
}

permission-gate

Asks before dangerous bash commands run: recursive deletes, sudo, and chmod or chown with 777. Returning {"block": true, "reason": ...} from a tool_call handler stops the call, and the model sees the reason as the tool’s result. The handler awaits a dialog with op, and blocks the command when no one can answer, in print and JSON modes:

#![allow(unused)]
fn main() {
api.on("tool_call", |event, ctx| async move {
    let command = event["input"]["command"].as_str().unwrap_or_default();
    if event["toolName"] != "bash" || !is_dangerous(command) {
        return Ok(None);
    }
    if !ctx.has_ui() {
        return Ok(Some(json!({
            "block": true,
            "reason": "Dangerous command blocked (no UI for confirmation)",
        })));
    }
    let title = format!("⚠️ Dangerous command:\n\n  {command}\n\nAllow?");
    let choice = op(
        "ui.select",
        &json!({"title": title, "options": ["Yes", "No"]}),
    )
    .await?;
    if choice != "Yes" {
        return Ok(Some(json!({"block": true, "reason": "Blocked by user"})));
    }
    Ok(None)
});
}

todo

A todo tool with list, add, toggle and clear actions, and a /todos command that shows the list in a component until Escape closes it. Each result carries the whole list in its details.

When a session starts, or the user moves through the session tree with /tree, the extension reads the current branch and takes the list from the last todo result on it. Every branch therefore keeps its own list:

#![allow(unused)]
fn main() {
fn rebuild() -> Result<(), String> {
    let branch = request(
        "session.read",
        &json!({"method": "getBranch", "args": []}),
    )?;
    let mut state = State { todos: Vec::new(), next_id: 1 };
    for entry in branch.as_array().into_iter().flatten() {
        let message = &entry["message"];
        if entry["type"] == "message"
            && message["role"] == "toolResult"
            && message["toolName"] == "todo"
        {
            let details = &message["details"];
            state.todos =
                details["todos"].as_array().cloned().unwrap_or_default();
            state.next_id = details["nextId"].as_u64().unwrap_or(1);
        }
    }
    STATE.with(|cell| *cell.borrow_mut() = state);
    Ok(())
}
}

Two handlers rebuild the list, one when a session starts and one after /tree:

#![allow(unused)]
fn main() {
api.on("session_start", |_event, _ctx| async { rebuild().map(|()| None) });
api.on("session_tree", |_event, _ctx| async { rebuild().map(|()| None) });
}

countdown

A countdown tool that counts down from seconds and shows each second as progress. When the user aborts the run, it stops with its own result, such as Stopped with 7 seconds left, and its details name the call with Context::tool_call_id.

#![allow(unused)]
fn main() {

Add yapi’s skills to your agent

The repository ships two Agent Skills that teach a coding agent to work with yapi. yapi and Pi load them, and so do other agents that read Agent Skills, such as Claude Code. This page covers what each skill does, how to install it and how to load it in a task.

What each skill teaches

Each skill comes with a helper script:

Install the skills

In yapi or Pi, install the repository at a release tag as a package:

yapi install git:github.com/SkymanOne/yapi@v0.4.2

yapi clones the repository but loads only its skills folder. A package installed at a tag stays at that tag through yapi update --extensions, so install a newer tag to update the skills. Installed without a tag, the package follows the main branch.

To use the skills without the rest of the repository, copy their folders into a skills folder, such as ~/.yapi/agent/skills/, ~/.agents/skills/ or, for Claude Code, ~/.claude/skills/:

cp -r skills/yapi skills/yapi-extension ~/.agents/skills/

With chest, add the skills to a project’s chest.toml, for yapi and any other agent that reads its skill folders. chest pins the commit and installs every skill the repository provides:

chest add git:github.com/SkymanOne/yapi@v0.4.2 --skill --name yapi-skills

--path skills/yapi picks one skill instead. Add -g to install them for every project.

Planned work

yapi implements Pi’s coding agent. This page lists the work planned beyond it: narrower capabilities, a package registry, a stable native extension API and Windows-specific features. The items have no dates and may change. The issue tracker tracks individual work.

Capability-based sandboxing

Extensions installed with chest run with the capabilities their manifest grants, and packages from yapi install keep Pi’s grants. The capabilities are coarse for now, so the plan is to narrow them:

  • File grants limited to paths and to read-only access, such as fs:read or a list of folders.
  • Network grants limited to hosts.
  • Process grants limited to programs, such as exec:git, so an extension can run one tool without all.
  • Extensions with identical grants always share pi.events. Once yapi scopes file and network grants, they’ll share only when their paths and hosts match too.

Security model and sandboxing describes the current model.

A package registry

A central registry of yapi packages will let chest.toml name packages and versions instead of npm or git sources.

Stable native extension API

yapi 1.0 will stabilize the native extension API: the Rust SDK and the host requests, which may change in any release until then. Asynchronous host calls will move to WebAssembly System Interface (WASI) Preview 3 as a new version of the Wasm Interface Type (WIT) world.

Platform support

Windows support is best effort. Windows-specific features, such as a PowerShell tool and native console input, will follow once the core is stable.

What each measure means

Each row of the tables measures one of these:

  • Startup, interactive: time from starting the interactive mode in a 100×40 pseudo-terminal until the footer shows the model.
  • Startup, print mode (to first request byte): wall time from starting -p "hi" until a local listener standing in for the provider receives the first byte of the request. It covers loading settings, credentials, the model catalog and the session, and building the request.
  • Keystroke to paint: time from writing a key into the pseudo-terminal until the character appears on screen, over 200 keystrokes 20 ms apart, in a session whose transcript renders about 10,000 lines. p50 is the median and p99 the 99th percentile.
  • Memory: resident set size (RSS) of the program and its child processes, as ps reports it, 2s after the first paint or, for the session of turns, 2s after the last answer.
  • Memory, idle: an interactive start with no session history and no extensions.
  • Memory, 10,000-line session open: the session of the keystroke measure, opened with --session.
  • Memory after 20 turns with tool calls: 20 prompts typed into the editor. A local mock provider answers each with a tool call, alternately read on a 1,000-line file and bash running seq 1 3000, and then with a Markdown answer holding a list and a code block. The mock checks that both programs make the same 40 requests.
  • Memory with 10 small JS extensions: 10 TypeScript extensions in the agent folder, each registering a tool, a command and an event handler.
  • Memory with Pi’s example extensions: 57 of the 70 single-file example extensions that ship in Pi’s npm package, loaded together from the agent folder. The benchmark leaves out the other 13:
    • five that replace the footer, header or editor, where the benchmark looks for the first paint
    • three that start commands, timers or file watchers when a session starts
    • one that commits to the working folder’s repository on exit
    • four that override a built-in tool that another example also overrides, which Pi refuses to load together
  • Install size: yapi’s release executable, which the release profile strips. For Pi, the published npm package and its dependencies installed with --ignore-scripts (121.8 MB, including prebuilt native modules for every platform), plus the Node.js executable it needs (124.8 MB on Linux).

For every measure with extensions, a first start fills the compile caches, and the benchmark doesn’t measure it.

How the benchmark runs

The method keeps the two programs’ conditions the same:

  • Every program runs with a cleared environment, a fresh home and agent folder, PI_OFFLINE=1, and a placeholder Anthropic key pointed at a local listener or mock provider, so no measure touches the network.
  • Startup measures run 20 times per program and memory measures 5 times, alternating between yapi and Pi, so drift on the machine affects both alike. Keystrokes run 200 times per program.
  • The report uses medians because single slow runs come from the machine rather than the program. On the macOS runner, single samples reach 128 ms for yapi’s interactive startup and 444 ms for Pi’s.
  • Pi runs from the same npm install whose size the benchmark measures, as its README recommends installing it. The example extensions come from that install too.
  • MB means 10^6 bytes.

Results vary with the machine. Compare yapi and Pi from the same run, not numbers from different machines.

Fix common problems

This page lists problems you can hit with yapi and chest, each with its fix. The last sections cover how to report a problem and where yapi writes its log.

Proxies, certificates and offline mode

yapi honors HTTPS_PROXY, HTTP_PROXY, ALL_PROXY and NO_PROXY, and the httpProxy setting. Requests to Amazon Web Services (AWS) container and instance metadata never use a proxy, as in the AWS SDK. yapi checks certificates against the operating system’s trust store.

--offline, or PI_OFFLINE=1, skips startup network work such as downloading fd and rg.

macOS blocks a downloaded binary

macOS marks an archive downloaded in a browser as quarantined, and Gatekeeper then refuses to open the yapi binary inside it, which Apple hasn’t notarized. The install script, curl and Cargo don’t set the mark. Remove it from the unpacked binary:

xattr -d com.apple.quarantine ~/.local/bin/yapi

No models available

yapi found no credentials. Set a provider’s API key or run /login. Choose a model lists the providers and how to connect each one.

An extension breaks startup

yapi -ne starts without extensions, including the built-in Model Context Protocol (MCP) and llama.cpp extensions. yapi config then turns the failing extension off.

A chest lock is stale

chest warns that entries aren’t locked, or that their lock is stale, when chest.toml lists entries that chest.lock doesn’t pin, or pins for another source, revision or version range. Run chest install to resolve them and update the lock, then commit chest.lock.

chest install --frozen, the default under CI, fails instead, so update the lock before you push. Lock, verify and update packages covers the lock.

Global skills or extensions are missing

When your global skills, extensions, prompt templates, themes or MCP servers don’t load, the run may be project-only. echo $YAPI_PROJECT_ONLY shows whether your shell turns the mode on, and unset YAPI_PROJECT_ONLY turns it off. To keep some global items in the mode, list them in the projectOnly setting, or press ctrl+o on them in yapi config.

When a global extension registers a provider, project-only runs lose that provider’s models. Keep the extension in projectOnly, or pick another model.

In print, JSON and RPC modes, the warning --project-only: the project isn't trusted, so none of its packages load means the project has files that need trust. Trust the project, or pass --approve for one run. Untrusted projects describes what such a run loads.

yapi finds two settings files

The error Both settings.json and settings.toml are in <folder>. Keep one of them. means that folder holds both files. With yapi closed, merge what you need into one of them and delete the other. Switch to TOML explains why yapi must be closed.

An extension’s call is refused

An error such as “Network access is not permitted for this extension” means the extension lacks a grant. A Pi extension without the file grant that reads or writes a file through node:fs gets an EACCES error saying that file access needs the fs grant.

Packages from yapi install have every grant. For an extension from a chest manifest, add the capability its call needs to the capabilities of its entry. What each capability allows lists each capability.

An extension misses events

A warning in the extension output that says an event did not reach an extension means routing kept a pi.events event from an extension that listens on its channel. It starts with what to change in the events of each chest entry it names, such as extensions.listener in chest.toml:

  • add "<channel>" to events.receive of <entry>, or events.send: add the channel to that list.
  • set events of <entry> to { receive = ["<channel>"] }: the entry is "isolated", so replace "isolated" with that table.

The warning names an extension that doesn’t come from chest by its file, and an entry of ~/.chest/chest.toml as extensions.<name> in ~/.chest/chest.toml.

Report a problem

Run /bug, or /bug <description>, to report a problem. It takes you through three steps:

  1. Describe what went wrong, or leave the description empty.
  2. Choose whether to include the session transcript. It holds your messages, model output, tool calls and their results, including file contents and command output.
  3. Without the transcript, the current model can write a summary instead. yapi sends the transcript to the model’s provider with your credentials and keeps only the summary.

yapi writes yapi-bug-report-<id>.zip to the working folder. The report can include your yapi version, operating system, the current model and provider configuration without API keys, loaded extensions, settings, and provider error diagnostics from the session. Its report.json leaves out API keys, tokens, passwords and other credentials. yapi keeps the transcript and the summary as written.

Unless yapi runs with --offline or PI_OFFLINE, and when the GitHub CLI is signed in, /bug then offers to open an issue on the issue tracker. A GitHub issue is public, unlike Pi’s private upload to radius.pi.dev.

The issue holds your description, the summary and report.json, with the names of your settings but not their values, and with your home folder written as ~. It never holds the transcript. Attach the zip file to the issue yourself if you want to share it, after you check it for private data. Otherwise, open an issue by hand and attach the zip file.

Run /debug to write the screen, the session’s messages and recent extension output to ~/.yapi/agent/yapi-debug.log. Check it for private data, then attach it to a report on the issue tracker with the output of yapi --version and your operating system.

Read yapi’s log

Start yapi with --enable-logging to append its log to ~/.yapi/agent/yapi.log, or yapi.log in YAPI_CODING_AGENT_DIR. Each line holds the time, the process ID, the level, where the message comes from, and the message. The log has extension output, extension runtime restarts and crashes, and warnings from yapi’s libraries.

Only you can read the file, as extension output can hold private data. yapi never shortens or removes it, so delete it when you no longer need it.

Contribute to yapi

yapi is a Cargo workspace whose crates mirror Pi’s packages. This page covers the tools you need, building and checking a change, where common changes go, comparing with Pi, releasing and building these docs. AGENTS.md describes the architecture, the design decisions and the rules for changes.

Tools you need

A build and its checks need these tools:

  • Rust stable. rust-toolchain.toml selects it with Clippy and rustfmt, and rustup installs it on the first build.
  • cargo-deny for the license and advisory check: cargo install --locked cargo-deny.
  • rg, fd and python3 on PATH for the tests.
  • prek for the git hooks: cargo install --locked prek or brew install prek. It installs the hooks’ own tools when they first run.
  • A checkout of Pi v1.0.0 (commit a13d35a) outside this repository. Read the matching Pi source before changing a behavior.
  • Node.js 22.19 or newer, only to record goldens from Pi or compare with Pi live.
  • A WebAssembly System Interface (WASI) SDK and the wasm32-wasip2 Rust target, only to rebuild the JS runtime with cargo xtask js-runtime.

The first build compiles about 420 crates, wasmtime among them, so it takes minutes rather than seconds.

Compare yapi with Pi

These commands run Pi and yapi side by side on every scenario, rewrite the goldens from Pi, and time yapi against the Pi binary at path_to_pi:

cargo xtask e2e --differential
cargo xtask e2e --record-pi
cargo xtask bench --pi path_to_pi

Pi installs from tests/fixtures/pi/generator with npm ci, which needs Node.js 22.19 or newer.

Release a version

A release takes these steps, in order:

  1. Set the new version in [workspace.package] of both Cargo.toml and guest/Cargo.toml. The extension SDK takes the guest workspace’s version, and the Release workflow fails when the two differ from each other or from the tag.

  2. Set the exact version requirements on yapi-ai, yapi-agent and yapi-core in Cargo.toml, such as =0.1.0, to the new version. They have no stable API, so each published crate requires exactly the versions it was built with. For a new minor or major version, raise those on yapi-types and yapi-tui in Cargo.toml and guest/yapi-extension-api/Cargo.toml too.

  3. Set chest’s version, which is its own, in crates/chest/Cargo.toml. Raise it, following semver, when git diff --stat v<previous> -- crates/chest crates/yapi-core crates/yapi-agent crates/yapi-ai crates/yapi-types lists changes. Otherwise keep it, and the release ships the same chest and skips publishing chest-cli, which crates.io already has.

  4. Update the versions that the yapi new template, the README and these docs pin. git grep for the old version lists them, such as git grep -n '0\.1\.0', which also finds the exact =0.1.0 requirements of step 2. They include the tag in pkg-url in crates/chest/Cargo.toml, which the Release workflow checks, so that each published chest-cli downloads the release that built it.

  5. Run cargo metadata --format-version 1 >/dev/null in guest to update guest/Cargo.lock, then cargo xtask js-runtime with a WASI SDK. The lock file is an input of yapi-js.wasm.

  6. In CHANGELOG.md, move the lines under ## [Unreleased] into a section for the release, with its date and link.

  7. Merge, then wait for CI on main to pass for the merge commit itself, which gh run list --branch main shows. The pull request’s green run doesn’t prove main’s. A flaky test is a bug to fix, not a run to repeat.

  8. Create the tag v<version> on the merge commit, signed with your key, and push it. Sign it before you push it, because pushing a replacement starts the Release workflow again:

    git tag -s v<version> -m "yapi <version>" <merge commit>
git verify-tag v<version>
git push origin v<version>

    The Release workflow builds and publishes the binaries and the documentation archive. Then it publishes yapi-types, yapi-tui, yapi-ai, yapi-agent, yapi-core, chest-cli and yapi-extension-api to crates.io with trusted publishing, so the repository stores no token. It skips each crate that crates.io already has at its version. Each crate has a trusted publisher on crates.io for repository SkymanOne/yapi, workflow release.yml and no environment.

Publish a new crate for the first time

crates.io accepts a trusted publisher only for a crate that exists, so a maintainer publishes each new crate once with their own token. The first publish of yapi-ai, yapi-agent, yapi-core and chest-cli has to come with a new workspace version, because the yapi-types 0.3.1 on crates.io is older than the code they build on. For that release, follow these steps, with v0.4.0 standing for its tag:

  1. Release as above. The Release workflow publishes yapi-types and yapi-tui, then fails on yapi-ai, which has no trusted publisher yet.

  2. Create a crates.io API token with the publish-new scope, then publish the four crates from the tag. Cargo publishes them in dependency order:

    git checkout v0.4.0
cargo login
cargo publish -p yapi-ai -p yapi-agent -p yapi-core -p chest-cli
cargo logout

  3. On crates.io, open each of the four crates’ settings and add a trusted publisher for GitHub: owner SkymanOne, repository yapi, workflow release.yml and no environment.

  4. Rerun the failed crates job of the Release workflow. It skips the four crates and publishes yapi-extension-api.

  5. Revoke the token on crates.io.

Build the documentation

This site lives in docs/, takes its configuration from book.toml and builds with mdBook. This serves it locally and rebuilds on each change:

mdbook serve

A workflow publishes it to GitHub Pages on every push to main. A pull request that changes it gets a preview, linked in a comment on the pull request.
